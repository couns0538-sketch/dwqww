## Algebra: the rule tightens as c_last grows

stop  <=>  t - B >= (G - C) * c_last   with G = 1.5, C = 1.3  =>  (G - C) = +0.2

Because G > C, a LARGER last iteration makes the rule stop SOONER. So 'c_last > soft' is
handled by the arithmetic itself — it is not a case the rule needs special-casing. What it
does need is that the search never loops: if a single iteration exceeds soft, the rule must
still allow ONE iteration to complete (otherwise a search whose iteration 1 exceeds soft would
stop with no move at all). That is a floor on the iteration count, not on the time.

## What the rule should do when the just-completed iteration already overran soft

The data answer: it stops, and it stops because of the algebra, not by luck. With G > C the
threshold grows faster than the projection, so a large c_last forces a stop. The ONE thing an
implementation must add is a floor: complete at least one iteration before any time rule can
fire, otherwise a search whose first iteration exceeds a very small soft plan would return
with no bestmove. That floor is already implied by the engine's iterative-deepening loop
(`for depth = 1; depth <= max_depth; ++depth` with the stop check AFTER the iteration), but it
must not be broken by placing the check before the first iteration.
