WHY THIS MATTERS
 * file 6 says a HANG is one of the few things that still counts as a multi-thread defect, and more
   importantly the owner's match program uses a clock -- a search that does not return will lose on time or
   make the driver kill the process. A band of counters where `go depth 22` never returns is exactly the
   kind of thing that corrupts a self-play or match run.
 * it is NOT the multi-thread variance file 6 ruled out: Threads 1 throughout.
 * it is not the EOF trap: each search is driven interactively and read to `bestmove`; the run is killed by
   MY 25 s cap, not by a closed pipe.

WHAT I HAVE NOT ESTABLISHED, and I will not overstate
 * whether it is a true infinite loop or an extremely slow search: at counter 70 the last line is
   depth 19 / 36.1 M nodes, so it IS still searching when the cap fires. I did NOT let it run to
   completion, so I cannot say whether it finishes at 60 s, 600 s or never.
 * the exact band edges: 60 DONE, 70 HUNG, 90 HUNG, 99 DONE. The edges are somewhere in (60,70) and (90,99).
 * whether it depends on depth 22 specifically, on PC20 specifically, or on the base build too -- I tested
   only depth 22, PC20, the PC build.
 * whether a clock limit (`go wtime`) makes it return: an un-timed search may simply be very slow, and a
   clock would cut it off. THAT IS THE NEXT MEASUREMENT AND IT DECIDES SEVERITY.
