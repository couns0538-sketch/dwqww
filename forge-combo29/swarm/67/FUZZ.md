## Method note: what a hang is, and is not

`no bestmove within T seconds` is **not** a hang. An unrestricted `go` (`go infinite`, `go mate 0`, `go` with no recognisable limit, `go btime` alone) is required to run until `stop`, so silence is correct behaviour.

A hang here is a **protocol-liveness failure**: after the case, the harness sends `stop` then `isready`, and the engine must answer `readyok` within 10 s. Every case in this report answered. The cases that merely ran without a limit are reported separately as *unbounded* (8 of 142).

This distinction was not academic: the first version of this harness used `no bestmove within T` and produced 7 false hangs, all of which turned out to be unrestricted searches that answered `stop` normally.

## Where the FEN refusal appears in the reply stream

The `info string invalid FEN` diagnostic is emitted **synchronously on the `position` command**, in both harness patterns. It never appears in the `go` output. This was measured by timestamping every reply line and attributing it to the most recent preceding write, not by reading text order.

| pattern | FEN cases | with refusal | silent | refusal owner |
|---|---|---|---|---|
| `P_isready` | 31 | 22 | 9 | position |
| `P_direct` | 40 | 27 | 13 | position |

`P_isready` = `position` → `isready` → `go`; `P_direct` = `position` → `go`. The pattern does not move the diagnostic. A harness that sends `isready` after `position` will read the refusal **before** its `readyok`, so a `readyok`-only read loop consumes it and discards it.

## Findings

### 1. No crash, no hang, no sanitizer line — in any class

142 cases on the base commit and 142 on `integrate/combo29-all`, every one under `-fsanitize=address,undefined`. Crashes: 0. Hangs: 0. Sanitizer lines: 0. Non-zero exits: 0. The engine answered `readyok` after `stop` in every case, and was still usable at the end of both runs (`nodes 400` from a fresh perft). Position arguments — including 70 KB tokens, embedded NULs, newlines inside a token, and 500 legal moves — did not crash or wedge either build.

The crash hazard in this area is therefore **not** a memory-safety one. It is the `0000` reply (finding 2) and the silent refusals (finding 3).

### 2. `bestmove 0000` is the reply for three distinct situations

11 of 142 cases produced `bestmove 0000`:

| situation | diagnostics before `0000` |
|---|---|
| checkmate | none |
| stalemate | none |
| `searchmoves` restricting to no legal move | `info string searchmoves restriction has no legal root moves` |

A front end must already know whether the position is terminal to tell these apart. Checkmate and stalemate are indistinguishable from each other on the wire, and stalemate carries no `info string` at all. `0000` is also, by convention, what a crashed or confused engine is reported as, so a naive front end cannot separate "game over" from "engine failed".

### 3. Malformed FENs are refused in silence above six fields

Below six fields the engine refuses loudly, on the `position` command. **Above six fields it refuses — or accepts — in complete silence.** There is no reply to scan, so no reply-scanning defence can catch it. This is the one class in this fuzz where the client has no observable signal at all.

The two builds even disagree about the outcome without disagreeing about the silence: the base commit searches the requested board, `integrate/combo29-all` searches the previous one. Both are wrong in a way the client cannot see.

### 4. A refused `position` leaves the previous board in place

On both builds an `info string invalid FEN` is followed by a search of the **predecessor** position. The `refused-after-good` cases fingerprint this with `go perft 2`: the search returns the predecessor's node count, not an error. A caller that validates nothing will therefore get a legal, well-formed `bestmove` for the wrong game.

### 5. Mid-search `setoption` truncates the search

`setoption` calls `stop_search()` before applying the value, so a `setoption` sent during a search ends that search. Measured: 16 `info depth` lines before the `setoption` write, `bestmove` emitted on the `setoption` write itself, and no further depth lines. The control without the `setoption` also stops when told, so the two are distinguishable only by timing. A GUI that adjusts an option mid-game silently loses the search it was waiting for.

### 6. Book moves make `bestmove` non-deterministic across runs

`OwnBook` defaults to true and the book RNG is seeded from `steady_clock`, so in game-search conditions two runs of the same position can return different legal moves. This is not a defect, but it means a *reply comparison* between builds is only sound when the position under search is also fingerprinted — which is why this report uses `go perft` for board identity and filters the cross-build table for substantive differences.
