## Method note: what a hang is, and is not

`no bestmove within T seconds` is **not** a hang. An unrestricted `go` (`go infinite`, `go mate 0`, `go` with no recognisable limit, `go btime` alone) is required to run until `stop`, so silence is correct behaviour.

A hang here is a **protocol-liveness failure**: after the case, the harness sends `stop` then `isready`, and the engine must answer `readyok` within 10 s. Every case in this report answered. The cases that merely ran without a limit are reported separately as *unbounded* (8 of 167).

This distinction was not academic: the first version of this harness used `no bestmove within T` and produced 7 false hangs, all of which turned out to be unrestricted searches that answered `stop` normally.

## Where the FEN refusal appears in the reply stream

The `info string invalid FEN` diagnostic is emitted **synchronously on the `position` command**, in both harness patterns. It never appears in the `go` output. This was measured by timestamping every reply line and attributing it to the most recent preceding write, not by reading text order.

| pattern | FEN cases | with refusal | silent | refusal owner |
|---|---|---|---|---|
| `P_isready` | 30 | 21 | 9 | position |
| `P_direct` | 66 | 31 | 35 | position |

`P_isready` = `position` → `isready` → `go`; `P_direct` = `position` → `go`. The pattern does not move the diagnostic. A harness that sends `isready` after `position` will read the refusal **before** its `readyok`, so a `readyok`-only read loop consumes it and discards it.

Across the whole corpus, **56** refusal lines were emitted; every one is attributed to `position` (counts: position=56). No refusal line is attributed to `go`.

The two patterns are deliberately unequal in size — the later truncation and field-count cases were added `P_direct` only, since the pattern had already been shown not to matter. The asymmetry is a property of the corpus, not of the diagnostic, and is reported rather than smoothed.

## Illegal moves in the `position ... moves` list

### Does an illegal move truncate the list or get skipped?

An illegal token is followed by more legal moves. Two hypotheses: the parser stops at the bad token (**truncate**), or it skips it and applies the rest (**splice**). They predict different boards, so the test is which recorded position the result equals.

`perft 3` is used because every legal prefix of the 4-move sequence has a distinct node count at that depth. `perft 2` does not: `e2e4 e7e5` and `e2e4 e7e5 g1f3 b8c6` are both 835, so a perft-2 test reports a false tie.

| illegal token at index | result | truncate predicts | splice predicts | verdict |
|---|---|---|---|---|
| 0 | 8902 | 8902 | 24079 | truncate |
| 1 | 13160 | 13160 | 24079 | truncate |
| 2 | 24825 | 24825 | 24079 | truncate |
| 3 | 23193 | 23193 | 24079 | truncate |
| 4 | 24079 | 24079 | 24079 | **ambiguous** (predictions coincide) |

Perft-2 reference values for the same prefixes, which is why the shallower depth cannot settle it:

| moves applied | perft 2 | perft 3 |
|---|---|---|
| 0 | 400 | 8902 |
| 1 | 600 | 13160 |
| 2 | 835 | 24825 |
| 3 | 779 | 23193 |
| 4 | 835 | 24079 |

### Junk between the sixth FEN field and the `moves` keyword

A bare-kings board has **3** legal moves, and the same board after `a1a2` also has **3** — because it is then Black to move with one king. So `perft 1` returns 3 whether the move was applied or dropped, and a perft-1 test cannot answer this question at all. `perft 2` can: 9 for the board alone, 15 after the move.

| position argument | perft 1 | perft 2 | moves applied? |
|---|---|---|---|
| `moves a1a2` | 3 | 15 | **yes** |
| `0 moves a1a2` | 3 | 15 | **yes** |
| `0 1 moves a1a2` | 3 | 15 | **yes** |
| `bogus moves a1a2` | 3 | 15 | **yes** |
| `bogus more moves a1a2` | 3 | 15 | **yes** |

The `perft 1` column is identical for every row, which is exactly the ambiguity. The `perft 2` column is what decides it.

## Two fingerprints that could not fail

Both of these produced a confident, wrong conclusion before being caught. They are recorded because the defect is in the **test**, not the engine, and it is invisible unless the measurement is repeated where the hypotheses diverge.

### Trap 1 — a perft depth that collides with itself

Question: does an illegal move truncate the move list or get skipped?

| moves applied | perft 2 | perft 3 |
|---|---|---|
| 0 | 400 | 8902 |
| 1 | 600 | 13160 |
| 2 | 835 ← collides | 24825 |
| 3 | 779 | 23193 |
| 4 | 835 ← collides | 24079 |

At perft 2, `2 moves` and `4 moves` are both **835**. A four-move spliced line therefore lands on the same number as the two-move truncated prefix, so the shallower depth cannot separate truncate from splice — and it silently agrees with whichever of the two the author assumed.

At perft 3 every prefix is distinct (8902, 13160, 24825, 23193, 24079), so the same experiment discriminates. The rule this yields: **a fingerprint must be checked to differ between the competing hypotheses before it is used to choose between them.**

### Trap 2 — a fingerprint that is equal by construction

Question: does junk between the FEN and `moves` drop the moves?

A lone-king board has **3** legal moves, and so does the same board after one king move, because it is then the other side to move with one king. So `perft 1` returns **3** in both cases (measured: 3 for the board alone and 3 after the move) and the test cannot distinguish "moves applied" from "moves dropped".

At `perft 2` the same two positions are **9** (board only) and **15** (after the move), which settles it. This is the purer form of the defect: the fingerprint was equal by the construction of the position, so no amount of care in running the test would have helped.

The rule: **before a measurement can confirm a hypothesis, state what it would have returned if the hypothesis were false.** If that value is the same, the measurement is not evidence.

## Findings

### 1. No crash, no hang, no sanitizer line — in any class

167 cases on the base commit and 167 on `integrate/combo29-all`, every one under `-fsanitize=address,undefined`. Crashes: 0. Hangs: 0. Sanitizer lines: 0. Non-zero exits: 0. The engine answered `readyok` after `stop` in every case, and was still usable at the end of both runs (`nodes 400` from a fresh perft). Position arguments — including 70 KB tokens, embedded NULs, newlines inside a token, and 500 legal moves — did not crash or wedge either build.

The crash hazard in this area is therefore **not** a memory-safety one. It is the `0000` reply (finding 2) and the silent refusals (finding 3).

### 2. `bestmove 0000` is the reply for three distinct situations

11 of 167 cases produced `bestmove 0000`:

| situation | diagnostics before `0000` |
|---|---|
| checkmate | none |
| stalemate | none |
| `searchmoves` restricting to no legal move | `info string searchmoves restriction has no legal root moves` |

A front end must already know whether the position is terminal to tell these apart. Checkmate and stalemate are indistinguishable from each other on the wire, and stalemate carries no `info string` at all. `0000` is also, by convention, what a crashed or confused engine is reported as, so a naive front end cannot separate "game over" from "engine failed".

### 3. An illegal move in the list truncates; the rest is dropped

A bad token in `position ... moves` stops the list: the legal moves before it are applied and everything after it is dropped, with one `info string` and no refusal. Verified at `perft 3` where all five legal prefixes have distinct counts — an illegal token at index 0, 1, 2 and 3 returns exactly the prefix value for that index. Index 4 is the one position where the truncate and splice predictions coincide, and it is reported as ambiguous rather than counted.

Junk between the FEN and the `moves` keyword behaves differently and is worse: the engine skips it and **applies the moves anyway**, silently. `position fen <board> bogus moves a1a2` reaches the same position as `position fen <board> moves a1a2`. So a malformed command can quietly become a real one.

### 4. Malformed FENs are refused in silence above six fields

Below six fields the engine refuses loudly, on the `position` command. **Above six fields it refuses — or accepts — in complete silence.** There is no reply to scan, so no reply-scanning defence can catch it. This is the one class in this fuzz where the client has no observable signal at all.

The two builds even disagree about the outcome without disagreeing about the silence: the base commit searches the requested board, `integrate/combo29-all` searches the previous one. Both are wrong in a way the client cannot see.

### 5. A refused `position` leaves the previous board in place

On both builds an `info string invalid FEN` is followed by a search of the **predecessor** position. The `refused-after-good` cases fingerprint this with `go perft 2`: the search returns the predecessor's node count, not an error. A caller that validates nothing will therefore get a legal, well-formed `bestmove` for the wrong game.

### 6. Mid-search `setoption` truncates the search

`setoption` calls `stop_search()` before applying the value, so a `setoption` sent during a search ends that search. Measured: 16 `info depth` lines before the `setoption` write, `bestmove` emitted on the `setoption` write itself, and no further depth lines. The control without the `setoption` also stops when told, so the two are distinguishable only by timing. A GUI that adjusts an option mid-game silently loses the search it was waiting for.

### 7. Book moves make `bestmove` non-deterministic across runs

`OwnBook` defaults to true and the book RNG is seeded from `steady_clock`, so in game-search conditions two runs of the same position can return different legal moves. This is not a defect, but it means a *reply comparison* between builds is only sound when the position under search is also fingerprinted — which is why this report uses `go perft` for board identity and filters the cross-build table for substantive differences.
