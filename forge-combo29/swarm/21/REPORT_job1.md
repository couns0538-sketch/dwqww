# REPORT job1 — area 1 (FEN INPUT under ASan + UBSan), seat 21, seed 2101

**What was asked.** 20,000 FENs derived from G and R by one random mutation each (replace,
insert, delete, swap two fields, drop a field; the mutation written beside it). For each:
`position fen` + `isready` (keep the answer lines), then `go depth 2` and wait for `bestmove`.
One process per 500 FENs; a crash restarts the process and is counted. Table: refused /
accepted and python-chess valid / accepted and python-chess INVALID (each listed) / crashes /
sanitizer lines / illegal bestmoves. Control: a 3,000-character first field must be refused
without a crash.

**The answer.** 18,775 of 20,000 mutated FENs are refused outright; 1,225 are accepted, of
which 1,186 are also valid for python-chess and 39 are not (31 adjacent-digit ranks, 8
seven-field FENs). 0 crashes, 0 hangs, 0 sanitizer lines, 0 genuinely illegal bestmoves on
this ASan+UBSan build. The control holds. The one behavioural fault found is not a parser
fault at all but a protocol fault, and it explains a wrong "known" number in the brief:
**a refused `position fen` leaves the old position on the board and still answers
`readyok`** — so the 8,902 in "impossible-castling FEN is ACCEPTED (perft 3 8,902 against
python-chess 8,802)" is startpos perft 3 from the refused command, not an impossible-castling
search.

**How sure.** High for the counts (they are the pasted output of the committed script over
the committed per-FEN table). High for the 8,902 provenance (case C shows a later legal FEN
does take effect, so the stale board is only between the refusal and the next good command).
Medium on one point I did not chase: whether any GUI actually sends `go` after a refusal
without reading `info string` — the engine's behaviour is what I proved, not the GUI's.

## Findings (each with the command that shows it again)

**21-F1 — the brief's 8,902 line is a refused command's left-over startpos.**
`python3 job1/f1_8902.py ~/b/release/forge out_f1`
On `rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBN1 w KQkq - 0 1` (castling rights but no h1
rook; python-chess perft 3 = 8,802) this build answers
`info string invalid FEN: castling right without king and rook` and then perft 3 = **8902**,
i.e. startpos. Case C, where a legal FEN is sent after the refused one, gives 170 — so the
stale board is exactly the window between a refusal and the next successful `position`.
The check that refuses it is `src/board.cpp:309-315`.

**21-F2 — a refused `position fen` keeps the previous game and still says `readyok`.**
`python3 job1/sticky.py ~/b/release/forge out_sticky`
Four refusal kinds (castling right without rook, rights with no rooks at all, three fields,
pure garbage) all leave perft 3 = 8902 after startpos, and a following `go depth 1` answers
`bestmove a2a3` — a move in the wrong game. `src/uci.cpp:40-42` prints the error and returns
without touching `board` (it works on `candidate`, which is discarded). I did not verify
that any GUI sends `go` this way; the engine-side behaviour is what is proved.

**21-F3 — accepted-but-invalid is a narrow, explainable class.**
`python3 job1/analyze.py job1/out_asan/asan_results.tsv tables_asan.md`
39 of 1,225 accepted: 31 six-field FENs with adjacent digits in the first field (Forge reads
`1P1` or `17` as consecutive empties), 8 seven-field FENs where the extra field is ignored.
All 39 are listed in `job1/tables_asan.md`.

**21-F4 — the 3,000-character control holds.** `job1/out_control/summary.txt`:
`invalid FEN: too many squares in FEN rank`, rc 0, no sanitizer line.

**21-F5 — the sanitizer proof for this seat.** `python3 job1/sanproof.py`. The planted copy
(`~/scratch/forge_planted`, two faults behind FEN text) is driven by the same `run_fen.py`
and yields `crash 2 / san 2`; the real build yields `crash 0 / san 0`.

## Suspicions, not proven

- Whether `board.cpp:309-315`'s strictness is right for *castling* specifically: it refuses
  a FEN whose rights are impossible, where FEN convention is to *drop* the impossible rights
  and play on. python-chess does the same strict refusal, so Forge matches it; but a GUI that
  pastes a sloppy FEN then silently plays the old position (F2). Not proven which behaviour
  the owner wants.
- The 8 seven-field FENs are accepted by `uci.cpp:36-38`'s six-token loop only because the
  7th token is read as the start of the `moves` scan and then dropped. I did not test a
  7-field FEN whose 7th token happens to be the word `moves`.
