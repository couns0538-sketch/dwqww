VERDICT — this CORRECTS my S-F26 claim, and it is the seventh self-correction.
S-F26 said "`go nodes 20000/50000/250000` and `go wtime 6000 winc 60` are all 3/3 reproducible in score, node
count and move". That is TRUE for the node limits and FALSE for the clock, as 6 runs per command show:

  go wtime 6000 ... : score 2 distinct values, nodes 2, depth 2, MOVE deterministic, ms 6 distinct
  go nodes 20000    : score/nodes/depth/move ALL deterministic (ms 2 distinct, i.e. only timing noise)
  go softnodes 2000 : score/nodes/depth/move ALL deterministic (ms 2 distinct)

So the accurate statement is:
  * `go nodes N` and `go softnodes N` are FULLY deterministic in score, nodes, depth and move (only wall time varies).
  * `go <clock>` is deterministic in the MOVE only. Score, node count and depth vary run to run, because the stop
    depends on the wall clock: one run finishes depth 16, another reaches 18, so the reported score differs by a
    few centipawns (55 vs 67; -292 vs -294) and nodes differ by ~80% (172,312 vs 309,981).
My earlier 3/3 was a small sample that happened to land on the same depth each time; with 6 runs the variation
shows. The move was stable in every run, which is the property a match actually depends on - so the match path is
still sound, but a training or analysis pipeline that records SCORES from clock-based searches gets run-to-run
variation, and should record them as approximate.

This also explains why the FINAL's "match results at Threads 1 are trustworthy" carries a caveat I originally got
wrong: the MOVES are trustworthy, the SCORES from a clock are not exactly reproducible.
