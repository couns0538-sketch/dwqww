THE MECHANISM, from include/forge/clock_plan.hpp:37-45 - the branch is `if (moves_to_go > 0)`. With movestogo 0 or
absent, `moves_to_go > 0` is FALSE, so BOTH take the else-branch:
    soft = available / TmSoftDivisor(22) + increment * TmIncrementPercent(75)/100      <- the 2.7-6.3% case
So `movestogo 0` cannot be distinguished from omitting the field by that test... yet the measurement shows they
DIFFER by 4x. That means the difference is NOT in plan_clock_budget's branch - it must be the UCI layer treating a
PRESENT `movestogo 0` differently from an absent one (e.g. setting limits.moves_to_go to something other than -1,
or a separate path). Worth flagging for whoever owns the UCI parser: my measurement and the code branch disagree,
which is itself the interesting part.
`movestogo 1` matching `movestogo 0` exactly is consistent with the same UCI-layer effect.

PRACTICAL: a match program must OMIT movestogo (or send a large value) rather than 0. Sending 0 costs 4-11x the
intended time and changes every match result. This is directly actionable for the owner's match path even though the
MATCH setting with the field omitted is fine.
