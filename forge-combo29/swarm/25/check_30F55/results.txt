absent, `moves_to_go > 0` is FALSE, so BOTH take the else-branch:

or a separate path). Worth flagging for whoever owns the UCI parser: my measurement and the code branch disagree,

*** THE CAUSE IS FOUND - it is the UCI parser, exactly as I suspected but had not read. ***

src/uci.cpp:172 and src/uci.cpp:241 BOTH do:   limits.moves_to_go = std::max(1, value)
So `movestogo 0` is CLAMPED TO 1, not passed through as 0.

And clock_plan.hpp:37 branches on `if (moves_to_go > 0)`, so:
  omitted  -> moves_to_go stays at its 'absent' sentinel (<= 0) -> else-branch:
              soft = 6050/22 + 60*75/100 = 320 ms
  movestogo 0 -> clamped to 1 -> if-branch:
              soft = 6050/(1+1) + 60*3/4 = 3070 ms   <- ~14x larger

Predicted ratio: 9.6x  |  Measured: 1514/179 = 8.5x, 1804/161 = 11.2x, 1892/381 = 5.0x

So the mechanism is EXACTLY the clamp: `movestogo 0` means 'one move to go', which budgets half the remaining
clock instead of a 1/22 share. It is not a bug in the time manager - it is the documented `max(1, ...)` guard
doing what it says, combined with a caller that sent 0 expecting 'unknown'.

PRACTICAL, now with the reason: NEVER send `movestogo 0` to mean 'unknown' - omit the field (or send a large
value). 0 is clamped to 1 = 'last move', which spends half the clock. The owner's matches omit it, so they are
unaffected; any harness that sends 0 is silently playing a different time control.
