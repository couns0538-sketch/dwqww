## Findings

### S-F4 — `Clear Hash` does not clear the move-ordering histories (area 7, `src/search.cpp:2666-2669`)
One sentence: `Searcher::clear_hash()` clears the transposition table and calls `worker->clear_caches()`, which
is only `evaluator_.clear()`, so the butterfly / continuation / capture histories, the killers and the
counter-move table survive a Clear Hash and steer the next search.
Shows it again:

```
python3 forge-combo29/swarm/27/job2/f3_tt_vs_histories.py /agent/repos/base/build-release/forge \
        forge-combo29/swarm/27/job2/O200.fens /tmp/f3 --depth 10 --limit 20
```

| variant (all after one warm-up search on one position) | bestmove differs from a fresh game | nodes differ | score differs |
|---|---|---|---|
| no clearing at all | 8 of 20 | 20 of 20 | 20 of 20 |
| `setoption name Clear Hash` | **9 of 20** | **20 of 20** | **19 of 20** |
| `ucinewgame` (baseline) | 0 of 20 | 0 of 20 | 0 of 20 |

The second row is the finding: the transposition table *is* gone, and the answer still differs from a fresh game
in 9 of 20 cases — so it is the histories, not the table. (`Clear Hash` is the command a GUI sends between games,
and the one a user sends before analysing a position they believe was already seen.)

### S-F5 — the same position, same depth, same options answers differently depending on what was searched before it (area 7, histories on `Worker`)
One sentence: with S14, Threads 1, Hash 16, depth 10, each of the first 40 positions of O searched in a fresh
process versus in one process after a single warm-up search gives a different node count in 40 of 40 cases, a
different score in 38 of 40 and a different bestmove in 14 of 40.
Shows it again:

```
python3 forge-combo29/swarm/27/job2/f2_history_drift.py /agent/repos/base/build-release/forge \
        forge-combo29/swarm/27/job2/O200.fens /tmp/f2 --depth 10 --limit 40
```
Result: `bestmove differs : 14 of 40`, `nodes differ : 40 of 40`, `score differs : 38 of 40`, cp delta median 8,
max 27. Table: `job2/f2/table.txt` (40 rows, every cold/warm pair).

This is not a bug by itself — every engine with history heuristics has it — but it falsifies any claim that a
single `go depth N` row is "the engine's answer" for that position, and it is why the "cold" column in job 1's
tables must be reproduced with `ucinewgame`: my own job-1 tables did send `ucinewgame` before every `go`, so they
are cold rows.

## The repair (text patch only)

`job2/clear_hash.patch.txt` against `6b98f217`: `Searcher::clear_hash()` calls `worker->clear()` instead of
`worker->clear_caches()`. `patch -p1 --dry-run` and `patch -p1` both return 0 on a clean `forge-combo29`.

| measurement | base | patched |
|---|---|---|
| bench 11 / 13 / 16 | 312866 / 862329 / 3024920 | 312866 / 862329 / 3024920 |
| perft 5 | 4865609 | 4865609 |

Raw: `job2/f3_patched/RESULT.txt`, `job2/honesty_clearhash/`.

**The design question, stated plainly:** clearing the histories on `Clear Hash` makes the command mean "forget
everything", which is what its name says and what a GUI's "new game" needs; it costs nothing in strength (the
histories rebuild in a few thousand nodes) and it makes analysis reproducible. The argument against is that
some GUIs send Clear Hash for memory reasons only, once per game, and losing the learned ordering costs a few
nodes at the start of each game. I recommend the patch; Opus decides.

## Suspicions, not proven

- `apply_history` (`src/search.cpp:245-249`) computes `entry + clamped - entry * std::abs(clamped) / HistoryMax`
  in `int`. Every intermediate fits in `int` for the allowed ranges, so I could not produce an overflow; the
  formula is the standard gravity update and is fine, but the `*` is the one place in the file where a future
  parameter change (HistoryMax small, bonus huge) could overflow. No test shows it today.
- `pick_best`'s AVX2 path only handles `index_ - list_start_ < 4`; for longer lists it falls back to `std::sort`
  with a strict `>` comparator, which is **not stable**. That is upstream of seat 06's S-F8 tie-break observation
  and consistent with it, but I did not build a position where two equal-scored quiets swap and the bestmove
  changes; seat 06's S-F8 stands on its own evidence, not on mine.
- Killers are copied into the picker at construction and never validated against the current position beyond
  `is_pseudo_legal` (`:586-587`). I could not construct a case where a stale killer is pseudo-legal but illegal;
  `next()` calls `board.is_legal(move)` before searching, so the safety net is there.
