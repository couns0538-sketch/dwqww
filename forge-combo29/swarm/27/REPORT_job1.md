## Findings

### S-F1 — a drawn root is reported as a completed deep search (area 7, `src/search.cpp:2251-2270`)
One sentence: when the root position is already a draw by repetition, by the fifty-move rule, or by insufficient
material, the engine emits one `info depth` line for **every depth up to the limit** with `nodes 0` and an empty
`pv`, i.e. it claims depths no search reached, and then plays the first legal move in generation order.
Shows it again: `bash forge-combo29/swarm/27/job1/f3_root_draw.sh /agent/repos/base/build-release/forge /tmp/f3`
Table from that script's raw files:

| case | info lines | last info line | bestmove |
|---|---|---|---|
| `R_repeat_root_depth10` (startpos three times after `g1f3 g8f6 f3g1 f6g8 g1f3 g8f6 f3g1 f6g8`) | 10 | `info depth 10 seldepth 10 score cp 0 nodes 0 nps 0 hashfull 0 time 0 pv` | `bestmove a2a3` |
| `R_control_depth10` (same list, one repetition shorter) | 10 | `info depth 10 seldepth 20 score cp 23 nodes 16231 … pv d2d4 …` | `bestmove d2d4` |
| `R_fifty_root_depth10` (`4k3/8/8/8/8/8/8/4K2R w - - 100 60`) | 10 | `info depth 10 seldepth 10 score cp 0 nodes 0 nps 0 hashfull 0 time 0 pv` | `bestmove h1f1` |

The control proves the ten lines are not a fixed shape: the same depth limit on a live position reports ten
lines with real node counts and a pv. `a2a3` is the first legal move: `go perft 1` from startpos lists `a2a3`
first. A GUI that shows "depth 10" therefore shows ten plies of analysis that never happened.

### S-F2 — a node budget under one root iteration answers the first move in generation order, silently (area 7, `src/search.cpp:2273-2277` and `:2639-2640`)
One sentence: `go nodes N` for N below the size of one root iteration (26 nodes at startpos for depth 1) returns
`bestmove a2a3` — the first legal move — with **no `info` line at all**, so nothing tells the caller the search
never rose above the first move of the generator's order.
Shows it again: `bash forge-combo29/swarm/27/job1/f4_budget_bestmove.sh /agent/repos/base/build-release/forge /tmp/f4`

| case | info lines | last info line | bestmove |
|---|---|---|---|
| `N_0` `go nodes 0` | 0 | — | `bestmove a2a3` |
| `N_1` | 0 | — | `bestmove a2a3` |
| `N_10` | 0 | — | `bestmove a2a3` |
| `N_20` | 0 | — | `bestmove a2a3` |
| `N_26` | 1 | `info depth 1 … nodes 26 … pv d2d4` | `bestmove d2d4` |
| `M_1` `go movetime 1` | 5 | `info depth 5 … nodes 1001 …` | `bestmove c2c4` |

The step from `N_20` to `N_26` is the whole point: one node above one finished iteration changes the move from
`a2a3` to `d2d4`. This is the documented `go nodes 0` behaviour (an "immediate bounded answer") extended by
arithmetic to every budget below one iteration; I am not calling it a design error, I am recording it because a
caller that trains on `go nodes` labels gets `a2a3` from a budget it believed was a search.

### S-F3 — `hashfull` is a sample of the first 1000 clusters, and it says so only in the code (area 7, `src/search.cpp:2561-2572`)
One sentence: `hashfull()` counts occupied slots in the first 1000 clusters only, so the value a GUI sees depends
on the table size, and at `Hash 1024` the same search reports `hashfull 1` where `Hash 16` reports `46`.
Shows it again: `bash forge-combo29/swarm/27/job1/f2_probe.sh /agent/repos/base/build-release/forge /tmp/f2`, cases `D_hashfull_16`, `D_hashfull_1024`:
`Hash 16 → hashfull 46` and `Hash 1024 → hashfull 1` at the same `depth 13`, same `nodes 72062`, same pv.
This is the usual way engines sample it; recorded as a fact, not as a fault, because nothing is out of bounds.

## Suspicions, not proven

- `MovePicker::pick_best` (`src/search.cpp:816-863`) carries an AVX2 chunk scan with a hand-written lane shuffle.
  I convinced myself twice that the lane set was wrong and was wrong twice: `static_assert(sizeof(Scored) == 8)`
  holds, and `_mm_setr_epi32(1,3,5,7,0,2,4,6)` does bring the four `score` words into the low 128 bits. **No
  test shows a fault**, so this stays a suspicion and is listed only so the next reader does not repeat my hours.
- `score_from_tt` (`:188-199`) drops a hit whose mate score would leave the mate band. I could not build a
  position where that drop changes the line without a TT size or clock I do not control from the UCI side.
- `is_repetition(root_index)` (`src/board.cpp:1235-1248`) returns true on a *twofold* repetition once it is
  inside the search (`++count >= 2`). It is a deliberate early-draw shortcut, but it means scores near a
  repetition are not the scores of the real game; no test here proves a wrong move from it.
- The `-fanalyzer` "uninitialized `SearchInfo result`" warning is, as far as I can read, a false positive on a
  struct whose every member has a default initialiser. I did not manage to make it fire at run time.
