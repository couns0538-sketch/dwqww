THE TRIGGER IS FOUND, AND THE CAUSE WAS MY OWN POSITION KEY — it excluded the castling field
=============================================================================================
For a dozen findings I could not characterise which positions bail. The answer is that the bail is exactly "the root
really did occur three times", and my own occurrence counter was over-counting, because it dropped the castling field.

THE BUG, in one line
--------------------
Every fixture-validation in this seat computed a position key as:

    f = b.fen().split(' ')      # fields: 0 placement, 1 side, 2 CASTLING, 3 ep, 4 halfmove, 5 fullmove
    key = ' '.join(f[:2] + f[3:4])      # placement + side + EP  ... CASTLING (f[2]) IS NEVER INCLUDED

The key I used in `job57`/`job59`'s audits was intended as "placement + side + castling" and was written as
`f[:3]`. The key used throughout the FIXTURE VALIDATION was written as `f[:2] + f[3:4]`, which silently took the EP
field and skipped castling. So "root occurs 3 times, asserted" was really "placement+side occurs 3 times, asserted".

--------------------------

| case | engine verdict | occ by MY key (castling ignored) | occ CORRECT (castling included) |
|---|---|---|---|
| C1 / job-55 T2, `r3k2r/…/R3K2R w KQkq`, cycle `a1b1 a8b8 b1a1 b8a8`×2 | searched 17,601 | 3 | **1** |

**PATTERN: BAIL iff the correctly-counted occurrences == 3. 5 of 5.**

In C1 and M7 the first rook/king move destroys a castling right, so the three recurrences the engine sees are
`(KQkq)`, `(-)`, `(-)` — one occurrence under FIDE identity, not three — and the engine correctly searches. In M1, M4
and E2 the cycle never touches a king or rook, the field is constant, all three recurrences are the same position, and
the engine correctly bails.

Nothing about the engine was ever anomalous. **Every "anomaly" in 23-F112/F114/F115 — material, castling rights as a
conditioner, halfmove, sparse endgames — was the same artefact seen from different angles: my fixtures were not testing
the positions I labelled them with.**

WHAT SURVIVES, AND IT IS THE ORIGINAL FAMILY
---------------------------------------------
The drawn-root bail itself is untouched and now cleanly characterised: **on a root whose true (FIDE) identity has
occurred three times, the base returns 0 nodes with cp 0 and plays its generator's first move.** 23-F93, F96, F98, F100,
F101, F103, F105, F108, F110, F113 all stand — every one of them used a cycle that never disturbed castling (K+R v K,
bare kings, pawns), so their root counts were correct under either key. That is why the family's core reproduced
everywhere while its SCOPE kept failing to fit.

WHAT DIES OR IS RE-DERIVED
---------------------------
1. **23-F112 ("the bail does not fire on every threefold")** — the F112 board was not a threefold. Its cycle moved a
   rook off a1, so the true occurrence count was 1. The claimed scope limit is WITHDRAWN: the bail is not narrower than
   threefold.
2. **23-F114 ("castling rights are a conditioner")** — castling is not a conditioner on the engine; it is part of the
   POSITION IDENTITY, exactly as FIDE says. The one-board contrast in F114 is real and is explained by this row, not by
   a quirk. The sentence "rights sometimes prevent the bail" becomes "rights change whether the recurrence IS a
   repetition", which is ordinary correctness.
3. **23-F115 (the material ladder)** — unaffected as a measurement (all seven rungs bail) but its INTERPRETATION
   ("material is not the discriminator") is true only because the fixtures were valid there; it never needed to be
   explained.
4. **23-F113 (root-specific vs history-wide)** — unchanged in status but the reason is now clearer: what varies is
   whether the SEARCHED position repeated, which is root-specific by construction.

INSTANCE 26, and the worst of the family: **I validated every fixture with a key that was itself wrong, and the key's
error was invisible because it always returned a plausible number (3).** Every "asserted == 3" in this seat passed
because the assertion used the same broken key as the construction. The check and the thing checked shared the fault —
instance 22's comparator problem at the level of the validation gate itself.

THE FIX, applied and to be applied everywhere
----------------------------------------------
`chess.Board.fen()` field order is placement, side, castling, ep, halfmove, fullmove. The correct identity key is
**placement + side + castling** (`f[:3]`) — and for a strict FIDE reading, EP only when a legal en-passant capture
exists, which I have not implemented and now flag as a second, smaller latent over-count in the same key.

LIMITS: the 5-case table is the whole evidence; a wider sweep over all this seat's fixtures for castling-disturbing
cycles would confirm whether any other finding used one. That sweep is the immediate next step.

THE FIX, IMPLEMENTED AND PROVED — `validate.py` and `revalidate_core.py`
-------------------------------------------------------------------------
The lesson alone is not enough; the gate needs to exist. `job59/validate.py`:

- **IDENTITY** is FIDE identity: placement + side + castling, plus en-passant ONLY when a legal en-passant capture
  exists (the second latent over-count previously flagged, now handled).
- **INDEPENDENCE**: occurrences are counted twice — once from FEN strings by my own function, once by asking
  python-chess's `is_repetition(n)` about the board whose identity equals the ROOT's. **The two must agree or the
  fixture is a HARD FAILURE.**

Self-test, which is what makes it usable (`validate_selftest.out`):

| case | result |
|---|---|
| castling-neutral threefold, expect 3 | **PASS** — counted 3, python-chess 3 |
| castling-disturbing cycle, expect 3 | **correctly REJECTED** — counted 1, python-chess 1 |
| same cycle, expect 1 | **PASS** |

**Building the validator produced the comparator fault a fourth time, and the self-test caught it:** my first
`count_via_python_chess` asked `is_repetition(n)` on the FINAL board while my own counter asked about the ROOT. On a
castling-disturbing cycle those are different positions — root once, final position twice — and the validator reported a
false disagreement. Fixed by walking back to the board whose identity equals the root's. **Two counters only form a check
if they count the same object.**

CORE FAMILY REVALIDATED (`revalidate_core.out`): all seven core drawn-root fixtures pass `expect=3` under the corrected
validator — E1, E2, E3, E4, F96's W-3, M1, M4 — and the two known-bogus ones (C1/23-F112 and M7) are rejected. So:

**the family's core findings rest on genuine threefolds, verified this time by two independent counters that agree, and
the two "anomalies" that generated four scope explanations were never threefolds at all.**
