THE BAIL PUBLISHES THE FILTERED HEAD — and an empty `searchmoves` restriction produces `bestmove 0000`
=====================================================================================================
A protocol-level test of the source reading's ordering, without reading further. If `searchmoves` filters
`root_candidates` before the terminal branch, a drawn root with a restriction should publish the first GENERATED move
that passes the filter, not the unrestricted head.

Fixture: the validated threefold `1K6/8/8/3R4/8/8/8/k7 w` + `b8c8 a1b2 c8b8 b2a1` ×2 (`check_fixture(expect=3)` PASS).
Generator order from `go perft 1` on that position begins `d5d1, d5d2, d5d3, d5d4, d5a5, d5b5`.

| case | restriction | info lines | last nodes | bestmove | inside restriction |
|---|---|---|---|---|---|
| U | (none) | 10 | 0 | `d5d1` | n/a — generator head |
| R1 | `d5d8` | 10 | 0 | **`d5d8`** | yes |
| R2 | `b8a8 d5d8` | 10 | 0 | **`d5d8`** | yes |
| **R3** | `e2e4` (illegal here) | 10 | 0 | **`0000`** | — |

**P1–P3 all HELD.** The bail publishes the first generated move that passes the `searchmoves` filter, which is exactly
what `result.best_move = root_candidates.front()` predicts once `root_candidates` is the filtered generator-order copy
(`search.cpp:2203-2209`). So the mechanism is confirmed from the protocol as well as from the source: **the bail's move
is "first generated move passing the restriction"**, a precise statement a tool author can act on.

**P4 — the open question, answered and it is a finding: an empty restriction yields `bestmove 0000`.** With
`go depth 10 searchmoves e2e4` on a position where `e2e4` is not legal, the engine emits ten `info depth` lines
(`cp 0`, `nodes 0`, empty PV) and then

    info string searchmoves restriction has no legal root moves
    bestmove 0000

That is the `restricted_root_empty` flag the source reading described (`search.cpp:2210`, the only field in `SearchInfo`
that distinguishes this case), surfacing on the wire as a **null move**. `0000` is not a legal move in UCI and a naive
front end will either crash or silently drop the turn. I did not predict this and am recording it as measured.

WHY THIS IS WORTH A LINE FOR ANY FRONT END
-------------------------------------------
The drawn-root bail is normally diagnosable by the empty PV (23-F151). This case is the exception worth knowing: the PV is
ALSO empty and the score is ALSO `cp 0`, but the move is `0000` rather than a legal first move. So a front end should
treat `bestmove 0000` as its own condition — `info string searchmoves restriction has no legal root moves` is the only
signal that says which of the two it is, and it is an `info string` line, which brings it squarely into the driver page's
first rule (count the `info string` lines).

LIMITS: one board, one depth, base build; the restriction cases use a drawn root, so whether `0000` also occurs on a
NON-drawn root with an empty restriction is untested — the source suggests `restricted_root_empty` is independent of the
bail, but I have not measured it.

THE `0000` CASE IS GENERAL TO AN EMPTY RESTRICTION, NOT SPECIFIC TO DRAWN ROOTS
-------------------------------------------------------------------------------
The limit I flagged is now tested. Same board, same illegal `searchmoves e2e4`, at `go depth 10`:

| root | info lines | nodes | bestmove | info string |
|---|---|---|---|---|
| threefold (DRAWN) | 10 | 0 | **`0000`** | `searchmoves restriction has no legal root moves` |
| bare FEN (**NOT drawn**) | 10 | 0 | **`0000`** | `searchmoves restriction has no legal root moves` |

**So `bestmove 0000` is a property of the empty `searchmoves` restriction, not of the drawn-root bail.** On the
non-drawn root the engine would otherwise search (7,581 nodes on this board) and instead returns a null move. That makes
it a broader front-end hazard than the drawn-root family: any caller that builds a `searchmoves` list which can be empty
— a book filter, a "only these candidates" analysis mode, a UI that lets a user deselect all moves — receives `0000`.

The distinction the earlier table drew between the two empty-PV cases still matters, but the advice changes: it is not
"when the root may be drawn, watch for `0000`", it is **"any `searchmoves` invocation can return `0000`, and the
`info string searchmoves restriction has no legal root moves` line is the only signal"** — which lands squarely on the
driver page's first rule, count the `info string` lines.

EDGE CASES — and the stalemate one is worse than anything above
----------------------------------------------------------------
| position | restriction | info lines | nodes | bestmove | info strings |
|---|---|---|---|---|---|
| mate-in-1 for White | `e2e4` (illegal) | 10 | 0 | **`0000`** | `restriction has no legal root moves` |
| checkmate (game over) | `e2e4` (illegal) | 10 | 0 | **`0000`** | `restriction has no legal root moves` |
| **STALEMATE** | `e2e4` (illegal) | 10 | 0 | **`0000`** | **NONE** |
| startpos | `e2e4` (**legal**) | 10 | 9,021 | `e2e4` | none |

**The stalemate row is the worst case in the family: `bestmove 0000` with NO `info string` at all.** Verified the fixture
is a genuine stalemate (`is_stalemate()` true, `is_checkmate()` false, 0 legal moves), so the engine is being asked about
a stalemated root with a restriction that cannot be satisfied — and it returns a null move silently.

That breaks the one piece of advice the previous section gave. There I said the `info string` line is the only signal
distinguishing `0000` from an ordinary bail; on a stalemated root there is no such line, so **`0000` must be treated as an
error on its own terms rather than as something a diagnostic will explain.** The structural reason is in the source
reading: `restricted_root_empty` is set for the `searchmoves` case (`search.cpp:2210`), but the stalemate arm of the
terminal branch produces a score of `0` through a different route, and no string is emitted for it.

A legal restriction behaves sanely (9,021 nodes, `e2e4`), which is the control that keeps the rest of this table honest.

THE HAZARD IS ON THE PC BUILD TOO — so it is not a base-tree-only concern
--------------------------------------------------------------------------
The owner plays PC r15. Eight cells, both builds, `go depth 10`:

| case | base | PC r15 |
|---|---|---|
| startpos + `searchmoves e2e4` (LEGAL) | 9,021 nodes, `e2e4` | **identical** |
| startpos + `searchmoves e2e5` (illegal) | 0 nodes, **`0000`**, `info string` | **identical** |
| stalemate + illegal restriction | 0 nodes, **`0000`**, **no string** | **identical** |
| mate-in-1 + illegal restriction | 0 nodes, **`0000`**, `info string` | **identical** |

**Every cell agrees between the two builds**, including the silent stalemate case. So this is a property of the protocol
handling, not of the drawn-root repair or of the base tree — and it reaches the build the owner's PC actually plays.

That matters for how it is described in the write-up. The other three hazards on the GUI page are also present on the PC
build, but they were each demonstrated on it; this one now is too. A front end written against the PC build needs
`bestmove 0000` handled exactly as a front end written against the base does.
