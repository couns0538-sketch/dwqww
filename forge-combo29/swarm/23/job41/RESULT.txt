A CONTROL THAT PASSED FOR THE WRONG REASON, AND THE FAULT INSTANCE
------------------------------------------------------------------
On the first run the drawn board (`8/8/8/8/8/8/8/K6k w`) reported "no info" at all six depths on both builds, and the
script's own P4 line printed as though satisfied. The raw output shows why:

    info depth 1 seldepth 1 score cp 0 nodes 0 nps 0 hashfull 0 time 0 pv
    bestmove a1b1

The line ENDS at `pv` with nothing after it. My regex required ` pv (.+)$`, so every drawn-board line failed to parse
and the control "found no mate" because it read nothing at all. That is **instance 15 of the missing-parse-reads-as-a-pass
family** (23-F3 is the rule, 23-F73 was the last instance) — and it is the more dangerous shape of it, because the
control that was supposed to catch a broken harness was itself the thing being silently skipped.

Repaired, and proved rather than asserted: the parser now accepts a trailing `pv` with no moves, prints "cells actually
parsed: N of 48", and prints `HARD FAILURE` plus a non-result warning if any cell fails to parse. Re-run: **48 of 48
parsed**, and the drawn board then genuinely produces cp 0 cells with empty PVs and no mate on either build. The first
run's output is kept as `result_FIRSTPARSE_BROKEN.out` rather than deleted.

WHAT F86 SHOULD NOW SAY, in place of what it said
--------------------------------------------------
A `mate N` score does not guarantee the PV in that line is long enough to deliver mate, the shortfall can be large
(8 plies on one board, not merely one), and it is confined to the FIRST depth that reports the mate — one depth later
the PV completes and replays to a real mate. So a GUI or tool that replays PVs needs the replay check on the first
mate line it sees and can trust later ones more; a tool that trusts PV LENGTH as a proxy for the mate being delivered
is wrong exactly where the mate is newly discovered, which is the moment a user is most likely to be looking.

LIMITS: three boards, six depths, K+R/K+Q endgames only — all forced wins of the same family, so nothing here says how
this behaves in a middlegame where the "mate" is 20 plies out. Both builds at default options only. The one-ply-short
cells and the eight-ply-short cell are all reported above; I did not attempt to explain WHY the W2 cell is shorter,
which would need the search's PV-extension code and is not something this harness can see.
