# PATCH — drop the redundant per-line TranspositionTable::clear() in the MultiPV loop
#
# WHAT IT FIXES: with MultiPV > 1 the engine zeroed the WHOLE transposition table once per extra PV
# line per depth (src/search.cpp:2879, inside the loop opened at :2851). clear() walks every cluster,
# so the cost was (multipv-1) x depth full-table writes: measured 95-141 ms PER CLEAR, constant across
# depths and line counts. At Hash 1024 MB that made go depth 12 take 2274 ms at MultiPV 3 against
# 18.5 ms at MultiPV 1, for a byte-identical search tree.
#
# WHY IT IS SAFE: the alternative lines already own a SEPARATE table
# (alt_shared = std::make_unique<SharedSearchState>(hash_mb) at src/search.cpp:2730) and every search
# calls tt.new_search(), which bumps the generation itself. The cleared table was fresh on every line
# anyway, so the explicit clear was redundant work, not a correctness requirement. The lines stay
# distinct because the search_moves narrowing at :2871 excludes the earlier lines' moves.
#
# MEASURED PAYOFF (PC r15 tree + this patch, PC20, Threads 1, Hash 1024 MB, same eight cells):
#   MultiPV 2, depth 6/8/10/12: 847.7/997.9/1190.9/1332.8 ms  ->  423.5/402.4/412.4/436.8 ms  (2.0x-3.1x)
#   MultiPV 3, depth 6/8/10/12: 1310.1/1597.9/1939.3/2274.4 ms ->  470.3/519.3/458.9/542.6 ms  (2.8x-4.2x)
# The per-depth growth is gone (flat ~400-540 ms).
#
# REPRODUCIBILITY GAIN (the strongest argument, independent of the speed): at MultiPV 3 with a clock,
# near the collapse boundary the UNPATCHED engine is not reproducible -- 8 identical runs at Hash 256 MB
# gave depths {7, 11} with node counts from 5,395 to 47,818 (an 8.9x spread), while this patched build
# gave depth 13 with exactly 106,863 nodes on 8 of 8 runs (and at Hash 512 MB, depth 12 / 71,070 nodes,
# 8 of 8, where the unpatched build gave depth 1 on 5 of 5). Two identical searches that differ by 9x
# in work cannot be used as a measurement.
#
# INDEPENDENTLY CONFIRMED (seat 20, its own builds and its own harness, 5 fresh processes per cell):
#   - it read the same code site itself (src/search.cpp:2879 inside the loop at :2851);
#   - it reproduced my figures TO THE NODE: Hash 512 MultiPV 3, shipped depth 1 / 220 nodes 5 of 5,
#     patched depth 12 / 71,070 nodes 5 of 5; Hash 256 shipped depths [11,11,11,7,11] with nodes
#     [47818,47818,47818,5395,47818] (the same instability and the same 5,395-to-47,818 range),
#     patched depth 13 / 106,863 nodes 5 of 5;
#   - all four honesty pins unchanged on the patched build (312866 / 862329 / 3024920 / 4865609);
#   - MultiPV 1 is BYTE-IDENTICAL between the two builds (depth 17 / 288,912 nodes, 3 of 3 each),
#     which is exactly the control that shows the patch touches only the path it claims.
#   Evidence: forge-combo29/swarm/20/job57/CONFIRM_30C36.md + confirm_30c36.json.
#
# NECESSARY BUT NOT SUFFICIENT (measured by another seat on the PC r15 tree, pins unchanged):
#   Direction confirmed, MAGNITUDE refuted. This patch restores most of the lost depth but not the
#   throughput, and the collapse SURVIVES IN REDUCED FORM. Measured at MultiPV 3, nodes/ms:

#     Hash 1024: still 0 nodes/ms
#   The MultiPV 1 control stayed flat throughout, so the change remains correctly scoped.
#   It does NOT reach MultiPV 1's ~1,500 nodes/ms: 583 -> 29 -> 0 across those Hash sizes.
#   THE RESIDUAL IS NOT `alt_worker->clear()` -- I tested that and it failed. Removing the per-line

#   slightly WORSE at 64 and 256 (nodes/ms: C31 615/393/149/40 vs C44 658/358/128/23 across Hash
#   16/64/256/1024). So the obvious next suspect is ruled out, not merely unmeasured.
