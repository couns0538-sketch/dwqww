## MISMATCHES

### M1. The profile table's `evaluate` share is a row from a different function

| | |
|---|---|
| report says | `forward \`evaluate\` — 7.34%` in the §5b profile table |
| artefact | `swarm/08/v3/profile/gprof_flat.txt` |
| regenerated | **5.08%** for `forge::nnue::v3::evaluate(...)` |
| verdict | **MISMATCH** |

`7.34%` is `forge::MovePicker::generate_evasions()` — a different function, on the line directly
below. Two independent facts fix which is which:

- the `nnue::v3` group is stated as **21.46%**, and 21.46 **only closes with 5.08**:
  `8.47 + 6.78 + 5.08 + 1.13 = 21.46`. Substituting 7.34 gives 23.72.
- the call count on the row, **2,556,881**, is `v3::evaluate`'s call count in the same file —
  so the row's own call column contradicts its percentage.

**Correct value: 5.08%.** The sentence the number supports — "no single v3 function exceeds 8.5%"
— still holds (the largest is `apply_changes_pair` at 8.47), so the advice is unaffected. The
figure is wrong; the conclusion is not.

Seat 08's own `REPORT_v3_steps01.md` carries the same 7.34 against `evaluate`, so the error is
inherited from the source report rather than introduced at consolidation. Its "top individual
functions" line quotes `generate_evasions` at 7.34 **and** `evaluate` at 5.08, one line apart —
the table and the prose in that report disagree, and the prose is right.

### M2. `163 at-or-above would be 90.6%` is itself off by one — it is 164 at 91.1%

| | |
|---|---|
| report says | "**163 at-or-above would be 90.6%, and 90.0% is what the row's own CI table quotes**" |
| artefact | `swarm/61/evidence/pc20_pernode_180.txt`, printed `pernode` column |
| regenerated | **162 strictly above, 2 exactly 1.000, 164 at or above** |
| verdict | **MISMATCH** |

The main count in that paragraph — **162 strictly above = 90.0%** — is correct and reproduces.
The explanatory clause is not: 162 above plus 2 exact ties is **164 at-or-above = 91.1%**, so
"163 at-or-above" names a number that is neither the strict count nor the inclusive one. It was
built by adding one tie to 162 when there are two.

**Correct value: 164 at or above (91.1%).** This is the exact class you flagged — a count adjusted
by one for a tie that was not counted. The fix in the report got the headline right and left a
second, smaller instance of the same fault in the sentence doing the correcting.

### M3. `go movetime 0` is not "the same search as `go depth 5`"

| | |
|---|---|
| report says | "`go movetime 0` — depth 5, 896 nodes — **the same search as `go depth 5`** (identical depth, nodes, score, pv and bestmove; only the `time`/`nps` fields differ, 0 against 1)" |
| artefact | none; re-measured on the rebuilt base, 10 fresh processes |
| regenerated | depth **3** (215 nodes) ×3, depth **4** (404 nodes) ×3, depth **5** (1001 nodes) ×4 |
| verdict | **MISMATCH** |

A zero wall clock does not mean "no limit"; it means "stop at the first iteration boundary the
clock check sees". Which iteration that is depends on how long the process took to get going, so
the outcome is not a property of the command. In two batches of ten, depth 5 — the value the
report observed — appeared 3 and 4 times. Some runs emit **no `info depth` line at all**.

**Correct statement: `go movetime 0` is a degenerate zero-budget search whose reported depth is
whatever iteration happened to finish — 3, 4 or 5 on startpos, and occasionally no `info` line.**
It should not be used as an identity with `go depth 5`.

The **class** claim the trap exists for survives intact and is the more important half: a
malformed `go nodes` / `go mate` is **unbounded**, not a short default. That reproduces exactly
(§"MATCH" below). Only the `movetime 0` row is unstable.

### M7. The fuzz corpus is 167 cases, not 142

| | |
|---|---|
| report says | "**A FUZZ of 142 protocol cases on two builds** found ZERO crashes, ZERO hangs and ZERO sanitizer lines" |
| artefact | `swarm/67/evidence-asan-base.json`, `evidence-asan-integrate.json` |

This is an **understatement**, which is the direction that never trips a check: every guard in the

in the list because **a reader planning a fuzz corpus will size it from this number.**

## Two things this audit found in its own checks, recorded because they are the same class

**(a) I flagged three figures as mismatches that were my own bugs, and the fix in each case was to
read the artefact the way its producer did.** The picker median (32.74 vs the stated 32.9) is the
upper-middle order statistic of an even-length sample, not the interpolated median — both are
defensible, the difference is 0.2 points, and I now report it as a convention note rather than a
defect. The depth row and the Hash-8 node count were real but needed the right estimator and the
right scope before they could be stated. **A checker that reports its own error teaches the reader
to skip it**, so these are named rather than quietly dropped.

**(b) The `go movetime 0` finding only appeared because my first probe reported one value.** The
first single run said "depth 5, 1001 nodes" — matching the report, which would have been a silent
MATCH. Repeating it ten times is what showed the instability. That is the run's own rule about a
one-fixture sentence, applied to my own instrument: **the check that would have passed was the one
run once.**
