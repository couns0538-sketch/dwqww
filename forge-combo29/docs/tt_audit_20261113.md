# Transposition table: what was wrong, what was found, what changed

Branch `cursor/tt-audit-bounds-4ffa`. Base `fable/standalone-h512-20261111` at `efb2ff960037087299332bc6a44baea69441a17a`. Nothing was merged, and `LOCK.md` was not changed.

The audit covered score bounds, mate-distance handling, replacement, and collisions in `include/forge/search.hpp` and `src/search.cpp`. Three bugs were reproduced on the unchanged baseline objects in `/tmp/forge-base` before any fix was written. Other behavior that was inspected and left alone is listed below, with the reason.

The engine is forge combo29. Builds used g++ 13.3.0, CMake Release, `-O3 -ffp-contract=off -fno-fast-math -march=x86-64-v4`, and the same `FORGE_*` defines as the lock CMake file. Clang was not used: the default `c++` on this machine is Clang 18 and it cannot find `-lstdc++`.

The switches:

- `FORGE_TT_MATE_CLOCK` — refuse a stored mate that needs more plies than the halfmoves left before the 50-move draw.
- `FORGE_TT_STORE_TERMINAL` — write checkmate, and a finished no-move node, as an exact table score.
- `FORGE_TT_RESOLVE_SLOT` — at store time, update the entry that already holds this position, or else run replacement again, instead of writing the slot chosen at probe time.

## How a mate score is stored

`MateValue` is 32000. `MaxPly` is 128, so any score at or beyond `MateValue - 128` is treated as a mate. `ValueNone` is 32002 and means "no score", not a mate.

Search scores a mate from the current node: mate in 5 plies is `MateValue - 5`, and being mated in 5 plies is `-(MateValue - 5)`. Before the score goes into the 16-byte entry it is converted to a distance from the node that wrote it:

- a win of `MateValue - d` at ply `p` is stored as `MateValue - (d - p)`
- a loss is stored by subtracting ply, which makes the stored distance shorter by the same amount

Reading it back adds or subtracts ply so the caller sees the mate from its own node. A centipawn score is stored unchanged. The payload is an `int16` clamped to `[-32767, 32767]`. `MateValue`, `-MateValue`, and `ValueNone` all fit. A score of 40000 is stored as 32767. That clamp was checked and left as it was.

The position key does not contain the halfmove clock. Two positions that differ only by the 50-move clock share one entry. The entry does store the clock, capped at 100, and `score_usable` decides whether the saved score may be read at the current clock. Clocks below 90 share a score. A clock of 90 or more must match the stored clock. Clocks above 100 compare equal to each other because both sides of the comparison are capped at 100.

## Bug 1: a stored mate ignored the 50-move clock

### What the old code did

`score_from_tt(score, ply)` adjusted the mate for ply and then returned it. The halfmove clock was not an argument. `score_usable` could still reject the entry when the clocks disagreed under the rule above, but a mate stored at clock 0 is usable at every clock below 90. Once that check passed, a mate in 30 was handed back at clock 85 exactly as if the 50-move rule did not exist.

`Worker::is_draw` already knows the rule. At clock 100 the position is a draw unless the side to move is checkmated. A mate that needs 30 plies cannot be reached from clock 85: only 15 halfmoves remain, and the game is drawn on the 100th halfmove unless that move itself is checkmate. The table was asserting a win the rules do not allow.

The same error applies to a stored loss. A "mated in 30" score saved early in the game was reused when only a few halfmoves remained, so the side to move could be told it was lost when the 50-move rule would have drawn first.

### The search that showed it

Position `4k3/8/8/8/8/8/8/3QK3 w - - 85 40`, depth 5, 16 MB hash, one thread.

A clean search scored 994 centipawns in 691 nodes. That is a queen-versus-king advantage, not a mate. The root is a PV node, and this search does not cut off a PV node on a table score, so a poisoned mate was not printed as UCI `score mate`.

The same search was then repeated after writing two exact entries by hand:

- the root, depth 40, score `MateValue - 30` (mate in 30), stored clock 0
- every legal child, depth 39, score `-(MateValue - 29)` (the opponent is mated in 29), stored clock 1

Those distances do not fit in the 15 halfmoves left at clock 85. The old conversion still accepted them. The search scored 992 centipawns in 4933 nodes. The reported score stayed a centipawn score, but both the score and the size of the tree changed. The false mate was steering the search.

### What the fix does

`score_from_tt(score, ply, rule50)` is the only conversion. With `FORGE_TT_MATE_CLOCK` at 0 the clock is ignored and the old arithmetic remains, which is the lock binary. With the switch at 1:

- remaining halfmoves are `100 - clock`, or 0 once the clock is 100 or more
- a stored win whose distance `MateValue - score` is greater than those remaining halfmoves becomes `ValueNone`
- a stored loss whose distance `MateValue + score` is greater than the remaining halfmoves becomes `ValueNone`
- a distance equal to the remaining halfmoves is kept: the mating move is played at clock 99 and the opponent is mated, which is the same exception `is_draw` already makes
- distance 0, the already-mated score `-MateValue`, is kept even at clock 100, because that position is already checkmate

`ValueNone` makes the caller ignore the score. The saved hash move is left in the entry. The bad mate stays in the cluster until a later store is allowed to replace it, so a later probe at a clock where the mate still fits can use it. That also means the entry can occupy a slot that a shallow bound might otherwise have used.

Current Stockfish `value_from_tt` uses the same distance test (`VALUE_MATE - v > 100 - r50c`, read from master `src/search.cpp` on 2026-11-13) and then substitutes a tablebase-win cap. This engine has no tablebase scores. Returning `MateInMaxPly - 1` would still be a crushing evaluation, so the unusable mate is dropped.

A mate line that captures or pushes a pawn can still be legal when the stored distance is longer than the current clock, because those moves reset the clock. The table does not record that the line resets it, so the score is dropped and search has to find the mate again. That is the conservative side of the test.

With the switch on, the poisoned KQK search stays at 994 centipawns and 691 nodes, the same as the clean search.

## Bug 2: checkmate was never written into the table

### What the old code did

Both `Worker::qsearch` and `Worker::search` probe the table near the start and store the result near the end. Checkmate returned before that store.

In quiescence, after the move loop:

```cpp
if (in_check && move_count == 0) return mated_in(ply);
```

`mated_in(ply)` is `-MateValue + ply`. The function returned that value and never called `store`. The position that is checkmate — the side to move is in check and has no legal move — was absent from the table.

In the main search the empty-move case was the same shape:

```cpp
if (move_count == 0) {
    if (!excluded.is_none()) return alpha;
    if (root_node && root_restricted_) return 0;
    return in_check ? mated_in(ply) : 0;
}
```

Checkmate returned `mated_in(ply)`. A no-move node that is not in check returned 0. Neither value was stored.

`is_draw` runs before the probe at every non-root node, and at every quiescence node, including the root of a depth-0 search. It returns 0 for a repetition, for insufficient material, and for a non-checking position with no legal move. Those draws never reach the store, and they were left that way. A repetition draw is path-dependent: storing it as an exact score of this position would be wrong on a different path. The main search skips `is_draw` at the root, so the empty-move return there is root checkmate (`mated_in(0)`, which is `-MateValue`) or root stalemate (0). Non-root stalemate is caught by `is_draw` and does not reach this return. Non-root checkmate does: the side to move is in check, so `is_draw` does not call it a draw.

### The search that showed it

Position `7k/8/6K1/5Q2/8/8/8/8 w - - 0 1`. White plays `f5f8` and it is mate in one. A depth-3 search found that move and scored 31999, which is `MateValue - 1`.

The position after `f5f8` was then probed. `hit` was 0. The mate had been computed and thrown away. The next time search reached that position it had to walk the empty move list again. The same miss happened at clocks 0, 50, and 99; the mating move is still legal at 99.

### What the fix does

With `FORGE_TT_STORE_TERMINAL` at 0 the early returns are unchanged. With it at 1, the checkmate return stores first:

- bound `BoundExact`
- score `score_to_tt(mated_in(ply), ply)`, which is the stored value `-MateValue`
- move none
- qsearch depth 0 and eval `ValueNone`
- main-search depth equal to the depth of that node
- main-search eval `ValueNone` when it is checkmate, and the static eval when the empty node is a draw

Excluded-move nodes (the singular-extension search) still return `alpha` with no store. A root restricted to a move list that has no legal move still returns 0 with no store. Those are not checkmate or stalemate of the real position.

Exact replacement is unchanged, so a later exact store can overwrite this entry. The stored depth is the depth that was searched, including depth 0.

This store is what moves the lock pins. With all three switches compiled in, net-on bench depth 20 went from 12389307 nodes to 12117140, and depth 22 from 34048354 to 37041976. Rebuilding `search.cpp` alone, with the other fixes absent, showed that the whole depth-20 change is this store (12117140). At depth 22 this store alone produced 34867996. The numbers are in the bench section.

## Bug 3: store wrote the slot chosen at probe time

### What the old code did

A cluster is four 16-byte entries. `probe` takes the stripe lock, looks for an occupied entry with the same 32-bit tag, and on a miss chooses a replacement slot: the first empty entry, or else the entry with the lowest `depth - 4 * relative_age`. It copies that slot's index into the `TTProbe` and releases the lock.

Search then walks the tree. Child stores run before the parent store. Those children can be different keys in the same cluster, and they can fill the slot this probe reserved.

`store` checked that the probe still belonged to this table, this epoch, and this key, then wrote `cluster.entries[probe.slot]` anyway. It did not look at what was in the slot. The replacement decision was made when the cluster was empty, and it was not repeated when the cluster had changed.

`same_position` was computed against whatever now sat in that slot. If a different key occupied it, `same_position` was false, and the write replaced that entry even when the new store was shallow and the old one was deep. The depth-protection rule (`depth + 4 > entry.depth`, or an exact bound, or a generation change) only protects an entry that is still the same position. A stale slot made every incoming store look like a new position.

### The two stores that showed it

On a 1 MB table, two keys that land in one empty cluster were probed before either was stored. Both probes received slot 0, the first empty slot.

The second probe was stored first: depth 30, exact, score 222. That occupied slot 0. The first probe was then stored: depth 1, upper bound, score 111. It still believed slot 0 was its destination, so it deleted the depth-30 entry. Afterward the deep key missed and the shallow key held score 111.

A second case filled the cluster after the probe. The probe of a fifth key was taken while the cluster was empty, so its saved slot was 0. Four other keys were then stored at depths 30, 29, 28, and 27. The stale store of a depth-1 upper bound wrote slot 0 and destroyed the depth-30 entry, which replacement would have kept. The entry it should have replaced was the depth-27 entry.

This happens in real search because a node probes itself, then probes and stores its children, then stores itself. Any child whose key falls in the same four-entry cluster can steal the parent's saved slot.

### What the fix does

With `FORGE_TT_RESOLVE_SLOT` at 0, store still writes `probe.slot`. With it at 1, store holds the same stripe lock and then:

1. if an occupied entry in the cluster already has this 32-bit tag, update that entry
2. otherwise run the same replacement rule probe uses: first empty slot, otherwise the lowest `depth - 4 * relative_age`, ties keeping the earlier slot

An unchanged cluster picks the same slot the probe recorded, so a store that races with nobody writes the same place as before. Both the `FORGE_SPD_TT_NOTLS` body and the locked body use this choice. The live build sets `FORGE_SPD_TT_NOTLS=1`, which is the path bench actually runs. The slot is chosen under the same stripe lock as the write. No separate multi-thread race test was added.

The depth-30 entry survives both reproductions, and the shallow key is stored in a free slot or in the least valuable slot.

This fix also moves a pin, by a small amount on its own. The isolated rebuild changed net-on depth 22 from 34048354 to 34048352 and left depth 20 on the pin. Combined with the checkmate store, depth 22 became 37041976, which is more than either piece alone. Once mates are stored, the 50-move rejection and the slot choice interact. That is why all three switches stay off in the default binary.

## What was inspected and left as it was

These were part of the audit. They are recorded because they were checked, and they were not patched.

- Bounds are `BoundNone=0`, `BoundUpper=1`, `BoundLower=2`, `BoundExact=3`. The PV flag is bit 2 of `gen_bound`. The test round-trips all three occupied bounds and the PV bit. A lower-bound store clears the PV bit.
- Static eval is already clamped to the open interval below the mate band. A mate score cannot be confused with an evaluation.
- A shallow non-exact store does not replace a deeper score, depth, or bound of the same position. It does replace the move when the new move is not none. An exact store replaces a deeper entry of the same position regardless of depth. Both match the previous policy, and the test locks them in.
- Replacement quality is `depth - 4 * relative_age`, with `relative_age = (32 + generation - entry.generation) & 31`. A full cluster drops the lowest depth. After three `new_search` calls without a probe, a depth-10 entry (quality -2) loses to a fresh depth-0 entry. That is the existing aging rule, not a new one.
- Generation is 5 bits. Thirty-two searches make an unprobed entry look current, so the depth-10 entry then survives and the fresh shallow entry is the one replaced. Probe refreshes generation on a hit, which is why an entry that is actually used does not wrap into "current" by sitting idle. `new_search` increments generation and epoch and does not clear entries. `hashfull` still samples the first 1000 clusters and counts only the current generation.
- Qsearch stand-pat inside the window, with no best move, stays `BoundUpper`. Promoting that to exact would treat a position whose captures were pruned as an exact score.
- Qsearch has no `tt_depth >= depth` test. A deeper saved score remains usable at depth 0. That is the usual quiescence rule: depth 0 is the floor.
- Main-search cutoffs still require `halfmove_clock() < 90` in addition to `score_usable`. Qsearch uses `score_usable` only. The clock-sharing rule described above is unchanged. Non-mate scores are still shared across clocks below 90.
- The 32-bit tag is the low 32 bits of the key (`verification_key`). The cluster index is the high half of a 128-bit multiply by the cluster count. Bits between the low 32 and the bits that affect that multiply are not checked. On a 1 MB table, `key` and `key ^ (1 << 40)` are the same slot and the same tag, so they alias. Widening the tag would change the 16-byte entry and the lock layout. The test expects this collision. It is a limitation, not a fix.
- Two different low tags in the same cluster are stored separately. The test stores scores 11 and 22 that way and reads both back. The alias above is the case the tag cannot see.

## What is still wrong, or still limited

- The default `forge` binary leaves all three switches at 0. That binary still reuses mates that do not fit the 50-move clock, still drops checkmate on the floor, and still writes the probe-time slot. Enabling the checkmate store or the stale-slot fix changes published bench pins, so those switches are not the default and the lock files were not replaced.
- A mate that resets the clock by a capture or a pawn move is dropped when the stored distance exceeds the current clock.
- An unusable mate entry stays in the cluster until a store is allowed to replace it.
- Non-mate scores are still shared across clocks below 90.
- `key ^ (1 << 40)` aliases on a 1 MB table. The test expects that collision.
- Generation wraps after 32 searches. The age test expects an unprobed depth-10 entry to survive that wrap.
- Exact stores, including a depth-0 checkmate, still replace whatever entry the replacement rule selected.
- Qsearch stand-pat with no move stays an upper bound.
- Non-root stalemate, repetition, and insufficient material still return from `is_draw` without a store.
- Root PV search does not cut off on a TT score, so the KQK failure was a node-count and centipawn change, not a UCI `score mate`.
- No multi-thread race test was added.
- `TTAuditAccess` can read the cluster index and the verification tag. It is a test friend.
- This run did not change account settings, install persistence, or read credentials. Supermemory was unavailable and Adapter was not authenticated; no memory tools were used.
