# NullThreatVerify

One UCI check option, `NullThreatVerify`, default off. With it off, null-move cutoffs are the ones this engine already used. With it on, a null-move cutoff at depth below 14 is kept only when a cheaper enemy piece attacks a dearer piece of the side to move and a reduced search that does not use null moves also reaches beta. If there is no such attack, the cutoff stands, as before. At depth 14 and above the existing verification is unchanged.

## Where the idea comes from

Null-move pruning treats a fail-high after a pass, searched at reduced depth, as a cutoff. That step is Christian Donninger's null-move search ("Null Move and Deep Search", ICCA Journal 16(3), 1993). A pass is a bad witness in zugzwang, so the usual guard is a second, reduced search with null moves turned off; the cutoff is kept only if that search also reaches beta. Ernst Heinz describes that confirmation in "Adaptive Null-Move Pruning" (ICCA Journal 22(3), 1999). The Chess Programming Wiki page "Null Move Pruning" records the same verification search.

This task applies that confirmation below depth 14 only when a lesser enemy piece attacks a greater piece of the side to move. Those are the nodes where a pass can look safe while the side to move still has to answer a capture. The attack test is this engine's `attackers_to`. The values are this engine's `SeePieceValue` (pawn 100, knight 300, bishop 300, rook 500, queen 900, king 0). A king is not a material attacker or a material victim. Equal values are not "cheaper". No code, constants, or tables were taken from another engine.

The reduced depth is the same `depth - R` this engine already uses for its depth-14 verification. `R` is the null-move reduction already computed for that node. For a threat confirmation, null moves are refused for the whole of that search, not only at its root. Depth 14 and above still verifies exactly as before, including when the option is on.

## What changed

`forge-combo29/src/search.cpp`, `forge-combo29/src/uci.cpp`, and `forge-combo29/include/forge/search.hpp` only. The diff is 49 insertions and 4 deletions. The option is a check in the `uci` answer:

`option name NullThreatVerify type check default false`

`setoption name NullThreatVerify value true` and `value false` are accepted. Any other value is reported invalid and does not change the flag. The flag is read before the attack scan, so the scan does not run while the option is off. While it is off, `null_blocked_` stays false and the null-move condition does not consult it.

`forge-combo29/tests_r3_06/null_threat_verify_test.cpp` was compiled with the engine sources, `-O3 -ffp-contract=off -fno-fast-math -march=x86-64-v3`, and `-fsanitize=address,undefined`. It drives the UCI loop, checks the option line, and checks the three default counts, the changed `bench 13`, and the same three counts after the option is set back to false. It then searches 200 positions to depth 10 with the option on (Hash 16, one thread) and requires each returned move to be legal. Sixteen attack positions are checked directly. The start position is not a threat. A pawn, knight, bishop, or rook attacking a dearer piece is, including the position after 1.e4 e5 2.Nf3 Nc6 3.Bb5 a6. An equal minor, a queen attacking a rook, a king beside a rook, a rook blocked by its own pawn, and a pawn attacked only by a pawn are not.

A throwaway counter, compiled locally and not kept in the tree, showed the confirmation is entered. From the Kiwipete position at depth 10 it ran 9 times, and at depth 14 the blocked search contained child nodes as well as the confirmation root. Every move from that probe was legal. The counter was removed before the commit. The node counts below are from the tree without it.
