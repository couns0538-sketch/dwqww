## The result that matters

**600 Hash resizes between 1 and 1024 MB, in one long-lived process and in 300 separate processes: zero
sanitizer reports, zero crashes, zero illegal moves.** The resize path is clean under ASan+UBSan.

**But the long-lived process does not return the memory.** Model A's peak is 1957 MB and it stays there from cycle
99 onward even when the Hash is later set to 32 MB; model B, which starts fresh, tracks the Hash value closely
(1024 MB -> 1097 MB peak, 32 MB -> 105 MB peak). So a front end that cycles Hash values in one process keeps the
high-water allocation — harmless for correctness, but a real memory-footprint fact for anyone running 300 games in
one engine process.
