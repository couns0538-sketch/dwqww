    12	## What was wrong
    13	
    14	`TranspositionTable::probe` remembers a slot, then search continues, then `store` writes only that slot. The slot can be stale:
    15	
    16	1. A miss on `key_a` selects an empty slot.
    17	2. A different key in the same 4-entry cluster is stored into that slot.
    18	3. A later probe of `key_a` selects another slot and stores a deep entry.
    19	4. The first search stores a shallow result through the original probe. `same_position` is false, so the depth guard does not apply, and a second copy of `key_a` is written.
    20	5. The next probe walks the cluster from the front and returns the shallow copy. The deeper entry stays in the table and is never seen.
    21	
    22	That happens when a helper thread, or a nested search of the same position, stores `key_a` before the outer store. The proof builds that slot sequence on one thread.
    23	
    24	## Change
    25	
    26	In both store implementations (`store_body`, used when `FORGE_SPD_TT_NOTLS` is 1, and `store` in the other build), after the stripe lock is taken, the cluster is scanned for an occupied entry with this verification key. If one exists, that entry is updated. Otherwise the probe-time slot is used, as before.

A shallow non-exact store therefore does not overwrite a deeper score once it is aimed at the real entry. A store that is not admitted still replaces the move on that entry. That was already the same-position rule; it is not a second copy.
