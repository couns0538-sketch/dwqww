   124	[[nodiscard]] int score_to_tt(int score, int ply) {
   125	    if (score >= MateInMaxPly) return score + ply;
   126	    if (score <= -MateInMaxPly) return score - ply;
   127	    return score;
   128	}

   130	// score_to_tt() shifts a mate score by the ply where it was stored. Shifting it
   131	// back by the ply where it is read must stay inside the mate band. A value that
   132	// crosses MateInMaxPly is not a centipawn score, so this ply ignores the hit.
   133	[[nodiscard]] int score_from_tt(int score, int ply) {
   134	    if (score == ValueNone) return ValueNone;
   135	    if (score >= MateInMaxPly) {
   136	        const int adjusted = score - ply;
   137	        return adjusted >= MateInMaxPly ? adjusted : ValueNone;
   138	    }
   139	    if (score <= -MateInMaxPly) {
   140	        const int adjusted = score + ply;
   141	        return adjusted <= -MateInMaxPly ? adjusted : ValueNone;
   142	    }
   143	    return score;
   144	}

    12	## What was wrong
    13	
    14	`TranspositionTable::probe` remembers a slot, then search continues, then `store` writes only that slot. The slot can be stale:
    15	
    16	1. A miss on `key_a` selects an empty slot.
    17	2. A different key in the same 4-entry cluster is stored into that slot.
    18	3. A later probe of `key_a` selects another slot and stores a deep entry.
    19	4. The first search stores a shallow result through the original probe. `same_position` is false, so the depth guard does not apply, and a second copy of `key_a` is written.
    20	5. The next probe walks the cluster from the front and returns the shallow copy. The deeper entry stays in the table and is never seen.
    21	
    22	With `Threads` greater than 1 the main worker does not take the exclusive lease, so both workers use the locked `store`. One worker can hold a probe while the other fills that slot and writes the same position elsewhere. The original proof builds that slot sequence on one thread. The two-thread proof runs it on two threads.
    23	
    24	## Change
    25	
    26	In both store implementations (`store_body`, used when `FORGE_SPD_TT_NOTLS` is 1, and `store` in the other build), after the stripe lock is taken, the cluster is scanned for an occupied entry with this verification key. If one exists, that entry is the one updated. Otherwise the probe-time slot is used, as before.
    27	
    28	The replacement rule is unchanged: an exact bound, a different position, `depth + 4` above the stored depth, or a generation change still replaces the payload. A shallow non-exact store therefore does not overwrite a deeper score once it is aimed at the real entry.
    29	
    30	A same-slot store still refreshes the move when the new score is rejected. That is the old rule. A stale slot does not: a rejected shallow store leaves the deeper move, eval, depth, bound, and score alone. The first cut of this fix aimed the write at the right entry but still copied the shallow move onto it (the kept move was `8->16` with score 777). The pins were rechecked after that second change.

    32	No UCI option. The fix is always on. The three default pins did not move.
