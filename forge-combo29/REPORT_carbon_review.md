## 2. Suspicions, not proven

1. **`forge-combo29/src/search.cpp:1451-1472,1638-1661` and `forge-combo29/include/forge/search.hpp:106-119`**  
   - **Suspicion:** `TTEntry::score_usable` guards against 50-move horizon mismatches (`rule50_clock`), as noted by its comment (`// Not a repetition key`), but neither `Worker::search` (`line 1638`) nor `Worker::qsearch` (`lines 1451, 1468`) invalidates or verifies TT score cutoffs — even for cached `MateIn(k)` scores — when intermediate positions along the stored PV have since entered `board.key_history_`. If position `X` was stored with `BoundExact` (`Mate in 2` via `X -> Y -> Mate`) earlier in the game and 3 reversible plies later the defender can play `Z -> X` when `Y` has now occurred before, a non-PV TT cutoff at `X` returns the stale mate score instead of `0` (repetition draw at `Y`), blinding the defender to its unique drawing move.  
   - **Test that would settle it:** Construct a position `Y` with a unique quiet 2-move mate `X -> Y -> Mate` where from `Z` only `Z -> X` repeats `Y` while all other moves allow mate; run `position fen <Y> moves <to X>` + `go depth 8`, then without `ucinewgame` run `position fen <Y> moves <to Z>` + `go depth 6` and compare `bestmove`/score against a fresh-TT search.

2. **`forge-combo29/src/search.cpp:1723-1736,2341`**  
   - **Suspicion:** At `depth >= 14`, high-depth null-move verification runs `search(board, ss, depth - reduction, beta - 1, beta, false)` (`line 1734`) with `threat_gate == false` (`line 1723` checks `depth < 14`), so `null_blocked_` remains `false` and only `ss->null_move_allowed = false` is cleared on the current frame (`(ss + 2)->null_move_allowed` stays `true` from `line 2341`). Two plies inside the verification search (after one move by each side), `Worker::search` immediately re-enables unverified null-move pruning (`depth - reduction - 2 < 14`), defeating high-depth verification on 2-tempo zugzwangs.  
   - **Test that would settle it:** Build a source test comparing `go depth 16` with `null_blocked_ = true` unconditionally at `line 1732` versus unchanged `6b98f217` on a non-pawn 2-tempo zugzwang where a quiet move #2+ beats a `0 cp` root alternative.

3. **`forge-combo29/src/search.cpp:1673-1676`**  
   - **Suspicion:** `bare_king_mode` disables razoring, RFP, null-move pruning, shallow move-loop pruning, and LMR in bare-king endgames (such as KRK) so unsound pruned centipawn bounds are not written to `shared_.tt`, but `line 1673` gates `bare_king_mode` on `multi_worker` (`all_workers_->size() > 1`). In a `Threads = 1` game where move-ordering history is non-zero from prior moves (or after `Clear Hash` without `ucinewgame`), `Threads = 1` still executes all of those prunings and writes the same unsound TT bounds.  
   - **Test that would settle it:** Warm a single-threaded `Searcher(16, 1)` on 4 middlegame positions, call `clear_hash()` (preserving histories), search the 40 `krk_40_positions.txt` positions at `depth = 14`, and check against a KRK tablebase for missed forced mates.

4. **`forge-combo29/src/search.cpp:1929-1950`**  
   - **Suspicion:** In singular extensions, when `singular_score >= singular_beta` and `singular_beta >= beta` (`line 1948`), multi-cut returns `singular_beta` immediately without ever searching `tt_move` at the current depth `depth`, relying on a `BoundLower`/`BoundExact` TT entry up to 3 plies shallower (`tt_depth >= depth - 3`) plus a `(depth - 1) / 2` reduced excluded-move search. If `tt_move` fails at `depth` due to a tactical refutation just beyond `depth - 3`, multi-cut still fails high.  
   - **Test that would settle it:** Compare node decisions on tactical test suites between unchanged `6b98f217` and a build with `line 1948` (`else if (singular_beta >= beta) return singular_beta;`) disabled after pre-populating `shared_.tt` at `depth - 3`.

5. **`forge-combo29/src/uci.cpp:180-187,251`**  
   - **Suspicion:** `isready` calls `v3_ready()` and exits `uci_loop` (`return 2`, terminating the engine process without `readyok`) whenever `NNUEArch` is `true` and no v3 network is loaded yet. Because `"NNUEArch"` sorts alphabetically before `"NNUEArchFile"`, any tournament manager that sends UCI options in alphabetical map order and synchronizes with `isready` between options (`setoption name NNUEArch value true` -> `isready` -> `setoption name NNUEArchFile value ...`) kills the engine before `NNUEArchFile` is sent.  
   - **Test that would settle it:** Run `fastchess` / `cutechess-cli` with both `option.NNUEArch=true` and `option.NNUEArchFile=/tmp/test_v3.nnue` (alphabetical option order) and check whether `isready` is sent between `setoption` lines.

## 6. What I would test differently

1. Differential game-state fuzzing across **same-game move sequences** (retaining TT and histories across `position ... moves ...` without `ucinewgame`) against a minimax oracle on low-material tactical/repetition graphs to catch path-dependent TT and root-draw bugs.
2. Clock-boundary tests sweeping `wtime` across `[0, 2 * MoveOverhead + 5]` ms at `Threads` in `{1, 8, 64}` and `Hash` in `{16, 512}` with wall-clock assertions that `bestmove` both respects `wtime` and beats a blind first-move baseline on mate-in-1 positions.
3. Combinatorial UCI option-interaction matrix (`{UseNNUE} x {NNUEArch} x {DeadMaterial} x {OwnBook} x {MultiPV} x {Threads}`) asserting `eval` consistency with depth-1 search and checking book moves against `Board::is_repetition(0)`.
4. Adversarial UCI `go` token-stream fuzzing that checks **semantic invariants** (no `depth = 64` runaway when `wtime`/`btime`/`nodes`/`mate` is present on the line, even when another keyword lacks its value), rather than always appending `nodes 200` as `tests_t18/uci_fuzz.cpp` does.
5. MultiPV mid-iteration `stop` tests at every millisecond offset between depth `d` and `d + 1`, asserting `bestmove` never regresses to an unverified primary move and emitted `(score, pv)` pairs always belong to the same root move.
