Pawn-span-fill review invariants (before final stable-patch review).

For an enemy pawn on file f/rank r, the old expression `passed_pawn_mask(color,square) & ~forward_file(color,square)` contains exactly adjacent valid files at every rank strictly forward of r. Immediate pawn attacks start those files one rank forward. Inclusive same-file forward fill must therefore reproduce that old mask, including empty spans at the terminal rank and one adjacent file at a/h edges.

With unsigned 64-bit input, successive OR shifts by 8, 16 and 32 produce offsets 0 through 7 ranks. None changes a file; high bits fall off for White and low bits for Black. Every shift count is below 64. Both shifts and OR distribute over unions, so equivalence on all 128 color/square singletons proves the bitboard identity for arbitrary unions; rank subsets and dense/random boards additionally test the actual implementation and call contract.

The caller must use the enemy color and the unmodified enemy Pawn attack slot. Both colors' pawn attacks must be initialized before either piece evaluation; later piece-attack aggregation must not overwrite that Pawn slot. Pawn-cache hits must still initialize these attacks. Trace and ordinary/runtime evaluation must share the same piece-evaluation function, with outpost ranks, support requirement and score/trace accumulation unchanged. A value-preserving bitboard replacement must not alter packed-score or float operation order, Board/NNUE state, or parameter lifetime.
