# Forge 6.4.24 training/data audit

Scope: read-only inspection of the attached tools and repository source at the user-selected `1ab50b2dd64d9b2f752f7f1285f6968cad2fd792`. No implementation, engine/build/test/training execution, or validation-loss reproduction was performed by this auditor. Historical logs below are labeled historical. Search must stay unchanged.

## Findings

1. **The supplied Python trainer trains/export a standalone network, not the current residual engine.** `train_nnue.py:51–61` constructs a teacher/result probability blend; `:408–411` optimizes `sigmoid(net)` directly. There is no HCE input or offset, HCE-alone metric, residual target, or zero-correction initialization. `:329` defaults to H256 and `:223` emits `FORGE_NNUE_RESIDUAL 0`. Current `include/forge/nnue.hpp:16–22` defaults H128 and current weights declare residual1/H128. `src/search.cpp:616–620` returns standalone NNUE by itself when the flag is0, or adds the NNUE centipawn correction to HCE when1. Therefore the existing tools do not fulfill the residual-training task; manually changing only the flag would double-count the HCE already learned by a standalone model. Width mismatch is normally caught by compile-time assertions, not silently loaded.

2. **Game-level splitting is absent and cannot be authenticated from legacy rows.** `train_nnue.py:102–105` splits by BLAKE2b of the first four FEN fields. It avoids exact-position overlap but allows adjacent positions from the same game in train and validation. `forge_selfplay.py:391` creates a game token for UCI, `:478–482` queues completed-game records, but `:594–596` reduces them to triples. `OutputStore.append` (`:221–255`) globally deduplicates by first-four-field position hash and rotates files after any accepted row; the database keeps only hashes and file byte/line counts. Game IDs, plies, moves and game boundaries are not retained. FEN fullmove/side ordering or clock resets are not an authoritative replacement: filtered positions, deduplication, multiple workers and rotation make boundaries ambiguous. The old `.txt` data may be used for explicitly labeled position-split diagnostics; it cannot meet the requested game-held-out acceptance without original game metadata/PGNs or regenerated data.

3. **The existing C++ trainer has a different input and score-POV contract.** `tools/tune/nnue_train.cpp:234–254` expects whitespace `FEN WhiteResult WhiteScore` and negates scores on Black-to-move positions. The supplied generator and Python trainer use `FEN | STMscore | WhiteResult`. Direct input fails parsing at `|`; merely removing separators/reordering fields still flips Black teacher labels incorrectly unless STM→White conversion is explicit. The C++ trainer's residual HCE offset (`:257–260`) is correctly STM `K*HCE/400`, and it zero-initializes the residual output layer (`:300–305`). It therefore provides useful original residual logic but is not a direct reader for the attached self-play format.

4. **Filtering is only partially enforceable from the retained data.** The generator rejects in-check positions, capture/promotion best moves, mate/bounded scores and scores outside the configured cap (`forge_selfplay.py:377–382,411–415`). It still accepts quiet checking best moves. The Python trainer only checks FEN validity/results and applies no in-check/score/tactical filter (`:51–61`). Three-field rows discard the best move, so tactical-best-move eligibility cannot be independently reconstructed without a retained move or a new documented engine search. Do not silently treat all legacy rows as verified quiet. Generator/rescorer configure Threads/Hash but do not explicitly disable OwnBook (`forge_selfplay.py:444–448`, `convert_training.py:146–148`); book moves can lack a usable score. `ponder=False` is explicitly sent in normal generation.

5. **Training/validation reporting and schedule do not meet the requested experiment.** Teacher/result blend is fixed (default .75/.25), optimizer LR is fixed (default .001), and validation is the first configured number of batches in sorted file order (`train_nnue.py:339–348,390–395,439–453`). There is no cosine schedule/result-weight ramp and no HCE-only baseline. Compare HCE, residual+HCE, and optional net-only against exactly the same frozen objective/rows; report a fixed score-only metric separately from changing ramp-dependent training losses. Max-ply games are labeled draws (`forge_selfplay.py:356–363`); this is a documented label source, not an established bug, but it makes substantial outcome mixing a potential noisy target.

6. **Data sealing is not actually checked by the trainer.** `file_snapshot` (`:276–291`) checks only that a `.txt.md5` file exists and snapshots byte size. It does not verify that checksum or retain before/after content hashes. Same-size edits can change an epoch's data. Preserve immutable input SHA-256/count/sidecar bindings for a new training run; reject mismatched seals and changed inputs rather than describing existence as checksum validation.

## Contracts to retain

The Python feature formula includes kings, uses relative color, flips Black ranks with XOR56, and puts STM perspective first; it agrees with `include/forge/nnue.hpp:24–28`. White game outcomes are correctly converted to STM in `parse_sample`; no demonstrated Python result sign bug was found. The raw NNUE correction's scale is `400/2.25` cp per logit. The scale is not material-phase tapered: HCE itself is tapered, but the residual is added in centipawns. Keep int16 quantization scales4096/4096, half-away-from-zero export rounding and existing standalone loader compatibility. A residual loss can use `offset=HCE*2.25/400`, `residual_target=(STMsearch-HCE)*2.25/400`, and `sigmoid(offset+net)` versus the corresponding teacher/result objective; do not subtract HCE probabilities from teacher probabilities. Zero output weights/bias must reproduce HCE at initialization.
