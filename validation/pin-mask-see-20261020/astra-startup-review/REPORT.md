# Independent startup review of frozen candidate 16

The original TSan batch remains **FAILED: 8/9 CTests passed**. Its OwnBook test timed out waiting for its initial `uciok`, before any readiness, book-option, position, or search command. The underlying cause remains unlocated. No production fix, gate relaxation, strength run, or Elo claim follows from this review.

Scope: read-only review of repository instructions, frozen source, original output and diagnostic instrumentation. The reviewer ran no engines, builds, benchmarks, matches, Git commands, or archive operations. This report is its only written artifact. Frozen candidate source: `553caef144ae2e1b696ba35d7a0eb1a50a03fde9`; failed executable SHA256 recorded by the original driver: `0dfa0b4c81d8ba4deea4b7c835133b7ec0aa2b31e5c536a5ca8ae937e8b4319f`.

## Established facts

- `native/frozen-tsan-attempt1/ctest.stdout` reports OwnBook failure after 16.76 seconds and the other eight tests passing. `summary.json` reports CTest exit 8, with `TSAN_OPTIONS=halt_on_error=1:exitcode=66` and default deadlock detection.
- `/workspace/.cloud-setup/forge-pin-mask-tsan/ownbook-regression.json` has `checks: []`, `error: AssertionError('UCI response deadline exceeded')`, then the transcript order `> uci`, `> quit`, identification/options and `< uciok`. There is no sanitizer report or appended close error in these captured outputs.
- `tools/ownbook_regression.py:18–20` waits for `uciok` before sending `isready`. `tools/uci_regression.py:36–51` enforces a 15-second monotonic wait. The later JSON is written after cleanup, which permits another five seconds for process exit and up to two seconds for reader join. Thus a final captured `uciok` is compatible with a failed handshake deadline.
- The transcript timestamps neither the child's write nor the parent's read. Sent commands are appended before stdin write/flush; received lines are appended by the reader before queue insertion. Therefore `> quit` preceding all captured output does **not** prove the engine first wrote its output after `quit`.
- No close error means the recorded close call accepted exit status 0. The original helper does not assert the reader thread stopped after its join timeout, so complete byte-level capture cannot be proved retrospectively from that assertion.

## Startup path and relevance of candidate changes

`src/uci.cpp:125–155` constructs the board and searcher, loads the embedded book, then enters `getline`. `Board::Board` calls `attacks::init` (`src/board.cpp:78`), including deterministic magic-number searches (`src/bitboard.cpp:63,155`). The default searcher allocates a 32 MiB transposition table and a worker; the worker allocates and clears history/cache state (`src/search.cpp:230,550,1438`). Embedded-book loading copies 2,616 entries and sorts them (`src/book.cpp:121–137`, `src/book_data.inc:2`). These are concrete pre-command work sites, not measured culprits.

The identification branch emits `uciok` using `std::endl` (`src/uci.cpp:183`), so an omitted explicit C++ stream flush is not supported as the cause. `nnue::available()` returns a compile-time availability flag; float-weight conversion is function-local lazy initialization (`src/nnue.cpp:53–80`) and is not invoked by this identification path. Creating a Worker object here does not launch its search thread.

The frozen parent15 and candidate16 copies of `bitboard.cpp`, `search.cpp`, `book.cpp`, `nnue.cpp`, `include/forge/search.hpp`, and both Python drivers are byte-identical. The inspected UCI diff is the version string only; the board diff changes the body of `Board::see_ge`. No SEE call occurs on this initial handshake path. That weakens a direct SEE-algorithm explanation, but does not prove the candidate binary/environment was irrelevant to timing.

## Ranked possibilities, not diagnoses

1. **Child-side startup work took too long to reach/respond to the command.** Real initialization and sanitizer/runtime overhead exist before command handling. CPU scheduling, throttling, or memory delays could enlarge their wall time. There is no original per-stage timing, CPU accounting, pressure record, or child syscall timeline proving any particular cause.
2. **The parent's reader or response consumer was delayed.** A child can write timely output that Python observes or consumes late; the original queue/transcript design cannot distinguish this from late child output. No original Python-thread timing establishes this alternative either.
3. **A transient runtime, lock, or I/O stall occurred before response delivery.** This includes sanitizer/runtime startup and pipe-handling boundaries. Eventual normal identification and accepted exit 0 argue against a persistent deadlock or crash, but the retained logs cannot exclude a recovered stall. No sanitizer race, lock-order report, or source-level deadlock is demonstrated.

These ranks prioritize discriminating measurements; they are not probability estimates. Labeling this as confirmed host contention, an OwnBook defect, a SEE regression, a missing flush, or a TSan false positive would exceed the evidence.

## Minimal diagnostic and conditional action

The already authorized pair is appropriately narrow: one frozen parent15 handshake and one candidate16 run of the unchanged five-transition OwnBook body, under unchanged sanitizer settings and the original response/close deadlines, with a separate aggregate guard. Preserve original failure files; write new evidence separately.

The inspected observer logs process creation, stdin flush return, reader lines, queue insertion/removal, process exit and reader completion. The supervisor optionally traces child writes and parent reads with syscall timestamps. The original `until` and `close` implementations remain inherited, and the OwnBook test body is imported unchanged. Observation nevertheless adds logging, locks and strace scheduling overhead, so its timings are diagnostic timings, not a reproduction of uninstrumented conditions or a calibrated performance result.

Interpret a recurrence by locating the first late boundary: late child stdin read/write points toward startup/child execution; timely child output but late parent read/queue handling points toward observation/consumer delay. A syscall gap alone cannot separate CPU execution from descheduling. If that distinction remains necessary, the smallest subsequent *separately authorized* measurement is bounded per-process CPU/wait-state sampling around that identified gap; source-stage timing is appropriate only if a child-side gap has first been established. Do not widen the timeout, suppress TSan, change book behavior or patch SEE to make this symptom disappear.

No production repair is justified until the delayed boundary is known. If both cases pass, stop this authorized diagnostic rather than rerunning until success or claiming a root cause. One parent success is a useful comparator, not an estimate of the candidate's failure probability.

## Acceptance wording and limits

An isolated candidate16 OwnBook PASS can provide **finite, separately recorded coverage of those five transitions with the same functional assertions and deadlines**, provided hashes match, sanitizer output is clean, exit is 0, all five checks pass, and capture/cleanup are complete. Combined reporting may say: “Original TSan batch: 8/9 PASS, initial OwnBook handshake FAILED; isolated observed OwnBook: 5/5 transitions PASS; startup timeout not reproduced and cause unresolved.”

It cannot say “original TSan 9/9 PASS,” “all suites passed in the batch,” “startup fixed,” or “environmental failure proved.” A single uninstrumented full-batch pass, if later required and separately authorized, would also remain a new attempt alongside the original failure. Whether a gate permits separate coverage must be decided against its existing requirements; this review does not relax it. The hosted strength package remains pending review and unlaunched.

The absent original timing cannot be recovered from later successful runs. The user can provide an already captured contemporaneous system/trace log, if one exists; no hardware purchase or platform change is justified by this record. Correctness/startup evidence does not measure Elo. Beating Stockfish configured with `UCI_LimitStrength` and an Elo target of 3200 remains a separate, precisely configured strength experiment; neither an absolute Forge rating nor a +200 gap has been established here.

### Smallest separate candidate, after promotion SEE

Keep this as a later candidate with its own frozen parent. Promotion-recapture SEE remains the next production variable. A narrow initialization change would store two `constexpr std::array<Bitboard,64>` sets of successful Forge multipliers (128 values, 1,024 data bytes) and retain the current masks, shifts, per-square offsets, table sizes, runtime lookup and other initialization order. Extract the successful constants from the exact frozen Forge generator in a separately authorized offline helper; retain generator source/hash and extraction provenance. No helper was built or run during this audit.

At startup, assign each stored multiplier and enumerate each relevant occupancy once to fill the table with `sliding_attack`. This removes `Prng::sparse`, the top-bit rejection test and repeated candidate collision loops (`src/bitboard.cpp:50–108`), plus their temporary occupancy/reference/epoch bookkeeping. It retains 102,400 rook plus 5,248 bishop occupancy cases, or **107,648 one-time table-fill cases**, ordinary leaper/pawn geometry initialization, line/between tables, search-state allocation and embedded-book loading. Runtime `Magic::index` stays unsigned 64-bit masked multiplication followed by the existing right shift (`include/forge/bitboard.hpp:126–135`); no search-time algorithm change is intended.

No process counts or elapsed savings were measured. Removing repeated trial work should reduce ordinary initialization work, especially sanitizer-instrumented work, but the fraction of total startup time and wall-time benefit remain unquantified. Do not call this a fix for the unlocated timeout, a search-NPS improvement, or an Elo gain.

### Correctness requirements before accepting that later candidate

1. Generate or extract constants from Forge's exact square numbering (`a1=0`), edge-excluding masks, 64-bit wraparound multiplication and shifts. Preserve these formulas and per-square table offsets. Validate the constants independently; do not rely only on a successful generation or a table hash. The current generator shares a static `epochs` array across rook/bishop calls while resetting its local epoch counter, so a freshly rewritten generator must not be assumed to reproduce its exact accepted constants automatically. Extracting the existing successful constants avoids that provenance ambiguity.
2. Add an independent stepping-ray oracle that derives masks independently and checks every square and all 107,648 relevant occupancy cases. Require lookup equality, in-range indices, correct table bounds/offset totals, and collision compatibility: multiple occupancies may share an index only when their attack bitboards are identical. Also check edge occupancy, the origin bit and off-ray occupancy invariance; independently checking the masks prevents an incorrect candidate mask from shrinking the test domain unnoticed. Runtime fallback to searching for replacement constants would hide defective frozen data and defeat the intended removal of startup search.
3. Verify queen unions and line/between geometry, then run existing perft cases (`tests/tests.cpp:195–204`), exact parent search scores/moves/PVs/nodes, relevant complete Release/ASan/TSan suites and the Windows gates. The current searched tests contain perft and legal-move coverage but no dedicated exhaustive magic-table/oracle test; perft alone is insufficient for this change. Compare lookup outputs rather than requiring byte equality of unreachable table slots.
4. Preserve the initialization lifecycle contract. `attacks::init` currently has a non-atomic static Boolean and expects initialization before search access (`src/bitboard.cpp:112–116`; Board constructor at `src/board.cpp:78`). Do not combine a thread-safety/lazy-initialization redesign, BMI2/PEXT change, compressed tables or full attack-table serialization with the multiplier change. Subsequent initialization calls must leave tables unchanged.

If startup benefit later needs measurement, first isolate the initialization stage and retain before/after CPU time and wall time with identical build/settings. Existing instrumented handshake samples cannot supply that estimate. This audit ran no engine, build, generation helper, match or benchmark and changed only this report.
