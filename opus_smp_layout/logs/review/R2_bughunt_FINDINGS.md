(b) The delta criterion is exact. With x = D2'*M and y = delta*M (mod 2^64), D1'*M = x + y; writing x = xh*2^32 + xl, y = yh*2^32 + yl: high32(x + y) = (xh + yh + c) mod 2^32 with carry c = [xl + yl >= 2^32]. Equality with xh <=> (yh == 0 and c == 0) or (yh == 2^32-1 and c == 1). yh == 0: c == 0 is achievable (xl = 0), so "can collide". yh == 2^32-1: c == 1 needs xl >= 2^32 - yl, achievable iff yl >= 1. Hence can_collide(delta) == (yh == 0) || (yh == 0xFFFFFFFF && yl != 0) is exactly "there exists D2' such that the tags collide" (xl ranges over all 2^32 values because M is odd and the low 32 bits of D2' are free). While any other process holds the file open with a share mode that does not include Write (for example a .NET reader using File.ReadAllText / FileShare.Read, or a tool built on it), that CreateFile fails with ERROR_SHARING_VIOLATION, the exception propagates and the tool exits with verdict ERROR. The coordinator reports exactly this at 21:0x GMT: a `grep -c` on the live log ended the e4_OFF_netoff 12k run (re-run as e4_OFF_netoff_r2). Which reader share mode was involved there is the coordinator's observation, not reproduced by me; the writer-side fragility is in the code as read.
- Severity: MINOR. The evidence cannot lie (fail-closed, the verdict says ERROR and the body hash of a truncated run cannot match a full one), but a routine look at a live log aborts a long pinned run.
- Suggested fix: open each log once per session with `new System.IO.FileStream($path, 'Append', 'Write', 'ReadWrite')` wrapped in a StreamWriter (AutoFlush = $true, UTF-8 without BOM), store it in the $eng object, write lines to it and close it in Stop-OspdEngine. With a persistent writer that shares Read+Write, a later reader can open the file, and a reader that refuses to share Write fails on its own open instead of ending the run. Until then: read live logs only through `Get-Content` (FileShare.ReadWrite) and never through a tool that opens with FileShare.Read.
