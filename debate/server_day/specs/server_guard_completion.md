# Complete the server guard's operating and closing paths

**Scope.** The package already contains a guard, boot guard, launcher and unit, worker with a seal-only mode, packer, clock watch, control maker and terminal writer. Complete the guard's connections among these programs. This specification does not ask for another finalizer or another inventory writer.

**During production.** Prove effective room and close reserve at each new horizon and while work is running. Budget physical bytes and file entries for plain records and offers, temporary pieces, open slots, logs, schedule history and finalization. Under pressure pause new work soon enough for closing and preserve every sealed original. Measure group memory and restart bursts. Roll an over-limit worker between games and reduce concurrency while preserving slot identities. Test a STOP arriving during a retry delay and again at restart. No reservation may appear after the stop. Run only one writer per slot. After a genuine new boot permit only verified same-instance continuation with valid clock, boot evidence and journal. For a replacement machine use a separate run and pilot. A running worker must obey a valid tightened cutoff; a later horizon cannot lengthen it.

**At the fence.** Stop reservations at dispatch cutoff. A natural game ending after an early fence but before D keeps its normal disposition. The worker's watch stops its engine alone with the measured allowance. If the worker died, the guard must end and observe the entire owned group, including a surviving native child, by D. A later grace period may help collect paperwork but cannot permit an engine to search after D. Record a failed stop visibly. Once fenced, start seal-only recovery where the old group has exited and the slot is available. If a slot cannot reconcile, record its evidence. Wait for every slot to be ended or unreconciled; make the packer's last pass, then call the existing terminal writer, verify the footer and compressed bytes, and record the resulting hash in closure. If inventory creation fails, keep the originals, alarm and retain the precise unresolved conditions.

**Known answers to check before implementation.**

- One toy volume offers 100 allocation units. Existing items use 70, and closing plus the owner's floor require 20. Admitting 11 more units must hold; 10 fit exactly if all other measured headroom also passes. A lost home connection changes none of these credits or custody requirements. Four units left but five required new directory entries must similarly hold.
- Hold back an extension. The slot reaches its last authorized range and waits. Publish a valid extension within the accepted scope and both deadlines; first reservation is the next counter exactly once. A new schedule whose earlier cutoff passed while the guard waited immediately forbids a new game. Reboot must not grant an extra 23 hours.
- Kill the worker while native CPU is advancing and observe the actual child independently. At D there are zero live searching children. The worker process is allowed to remain alive long enough to record its reason where it survived. An ineffective group stop must fail the rehearsal even if no new output lines appear.
- Four reserved counters with g1 done and g2 durably failed yield one done, one unfinished, no dispatch-unknown and a never-dispatched tail g3–g4. With a previous play epoch and no line for g2, there is one dispatch-unknown instead. Repeating seal-only recovery changes neither result. With no earlier play epoch all unstarted counters remain never dispatched.
- Close two slots, one with all six known games and one seal-only from its first epoch with three never dispatched. Expect 462 raw rows, six done and three never dispatched. After the packer and terminal writer finish, the closure metadata must name the verified terminal hash. Removing the footer prevents a completed close.
