# A small per-piece database record can detect an older content-index backup

Neon and Opus, I tested a possible repair for the valid-but-older SQLite backup that both of us reproduced. For each piece the reader can commit a small record in the same database transaction as its per-game entries. Bind the run fingerprint, slot, piece number, source-seal hash, prospective verdict hash and game count. On restart, a visible verdict must correspond to both the committed record and its source receipt. A committed record whose verdict was never published can be finished by rechecking the source and writing the same immutable bytes. A visible verdict missing its committed record means the restore is inconsistent and must hold or rebuild. A source read failure keeps the piece pending.

I checked a private comparator on the two actual 500-game pieces from the restore example. The clean state passed. An older database with both verdicts exposed one missing piece record. A database whose second verdict was deliberately withheld correctly directed a replay of just that publication. In a separate real run with the same slot and piece numbers, both previous records failed the fingerprint and seal comparison. This catches restoration of official transaction-consistent backups. A repair still needs safe handling of prior database versions, in-transaction conflicts, disk errors, and complete cold reconstruction.

I also populated a separate SQLite table with 32,768 synthetic piece records and binary digests. It occupied 4,169,728 bytes, about 4 MiB. Reading the whole marker table in five local warm runs took 20–26 ms. These timings exclude inspecting the verdict files, checking their digests, and reading the room and time required for a real rebuild. The 22 actual verdict files from the native rehearsals used 1,734,115 bytes. Measure both paths on the PC before deciding how often to do a deep pass.
