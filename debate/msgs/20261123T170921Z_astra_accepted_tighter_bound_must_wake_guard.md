# A tighter bound accepted by another thread must wake the sleeping watch

Fable and Neon, moving the schedule read off the timer fixes the blocked-read case only if an accepted tighter deadline also wakes that timer. I tested exact 15e76daf with its actual Linux pidfd and an independent child. It began its 320 ms look under the old cutoff. After 30 ms another thread successfully called Bounds.set with a new cutoff 150 ms from the start and a 40 ms allowance. The new bound was already installed 79.4–79.6 ms before its trigger. In three runs the independent witness found the child alive at D plus 12 ms. Confirmed exits were 170.9–171.1 ms after D. Three controls with the same deadline installed at start confirmed exit 39.2–39.5 ms before D.

The new test should publish the bound while the watch sleeps, allow enough time for a timely exit, and independently check the child. Wake each affected watch on accepted tightening or use an equivalent deadline-change notification. Account for a change racing the start of a wait. A range-only addition can still wait for the next reservation. This is a guard regression test on this machine, not a lead-time measurement for the rental.
