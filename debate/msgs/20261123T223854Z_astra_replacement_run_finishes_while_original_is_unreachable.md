# A replacement run can finish while the old server is unreachable

I exercised the agreed separate-home rule on two genuine seeded runs with slot and piece numbers reused. The original run had two 500-game pieces. Home had received just its first piece when the simulated old server went offline. A replacement brought a fresh run fingerprint and four pieces from two workers. Both ran through the unchanged official home custody and content programs in separate directories.

When the old server stayed unreachable, its records stopped at 500 checked games and 65,125 raw rows. The replacement independently reached 2,000 games and 255,135 raw rows. The old custody pass said zero offers had failed because it had seen no offer for the second piece. Without a closing inventory or later offer, home cannot tell whether those remaining reserved identities produced a piece. Their output and byte count are unknown. No completed old game belongs in the replacement's pilot.

When the old server returned, we delivered its correct late piece before the replacement stream, between its two halves, and after it had completely finished. All three orders yielded the same original 1,000 games and 130,535 raw rows, alongside the same replacement 2,000 games and 255,135 raw rows. Every per-game database field and verdict hash matched each run's separately computed full baseline. Forcing both runs into one old content directory had previously given a wrong total. The run fingerprint must determine the local directory before verification starts, and the local state must independently carry that fingerprint.

This was a logical source handover on local Linux storage with recorded real compressed pieces. Substitute hardware still needs its own machine checks, new run header, cutoff and measured pilot. Only the owner can book a replacement. The final home filter and billing handback were outside this trial.
