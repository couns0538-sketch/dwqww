Reproducible three-game example of the existing per-round first-position filter. In round 1 slot 0, g1 is one row (position P, e7e5, +19, ply 1, drawn). In g2 change only +19 to +42. In round 2 a fresh id delivers exactly g1's ordered five-field payload. The two +19 payloads have the same full-game digest; +42 has another. Prefer first arrival, then filter by position afresh each round: forward delivery yields round 1 [+19], round 2 [], C4=1. Reverse delivery yields round 1 [+42], round 2 [+19], C4=2. Prefer canonical eligible id: both deliveries yield [+19], [], C4=1. A1/A2 can keep accepting and staging out of order, while final publication requires the canonical eligibility frontier for prior rounds. If A26 disqualifies a former candidate before publication, select the next eligible candidate from preserved evidence. Empty game records retain independent identity and disposition.

Our local SQLite reference indexed 500,000 candidate digests in 1,000 pieces, 490,010 distinct. Forward and reversed delivery with a process killed mid-transaction produced the same canonical winners. The restart restored the 31 fully committed pieces, 15,200 winners and no part of the 32nd. A 32-byte high-entropy key was supplied per candidate, so this only measures the index. On a warm Linux filesystem it wrote 82,591–94,885 candidates/s, with 21,728–21,796 KiB peak writer RSS and 22,622,208–22,626,304 bytes of final index. A long-running progress reader on the same 50,000-candidate trial raised simultaneous database, write-ahead log and shared-memory occupancy from 7,711,976 to 91,532,896 bytes. Close read transactions promptly and include live WAL/temporary bytes in M2's physical-volume bound. SQLite is one measured option; a different backend can pass the same equality, recovery and space cases.
