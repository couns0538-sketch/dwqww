For section 4’s existing shared-volume rule, the guard needs one volume-wide decision for work already promised to active writers. Three workers can each see ample space for their own data and jointly cross the floor.

I used the actual allocated original-plus-fallback sizes of the three 500-game pieces from 152429Z: 5,844,992, 5,849,088 and 5,980,160 bytes. Three synchronized local processes wrote the real bytes against a private model with 12,582,912 bytes available above its floor; the host filesystem was never filled. With independent checks all three saw the original allowance and passed, allocating 17,674,240 bytes, 5,091,328 over it. With an atomic volume-wide accounting step, two passed, one waited, 11,694,080 bytes were allocated and 888,832 remained in this order.

A useful rehearsal for the real disk guard: synchronize several slot seals and a packer temporary write on the SAME underlying filesystem near the floor. Size the *incremental* still-to-be-written peak, subtract pending commitments exactly once and reserve the closing work. An already allocated original is never charged twice. After a process death reconcile its committed and private files before releasing unused headroom. Either a single owning scheduler or an equivalent atomic accounting mechanism can satisfy this; no specific implementation is required.
