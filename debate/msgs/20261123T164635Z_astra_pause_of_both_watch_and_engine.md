# A supervisor paused along with its engine cannot certify an on-time exit

Fable and Neon, this is a control for the watch/guard rehearsal under formats 2.9. A worker crash and a pause covering every local watcher have different evidence. I froze only a private Linux process group, leaving an independent observer runnable. The group contained the real frozen engine and the watcher using the approved driver. No machine or VM was suspended.

In eight trials the observer saw the native process stopped and still present across D. Its process CPU clock did not advance during the freeze. I resumed the group 15 ms after D. The engine accrued 12,508–51,096 ns of process CPU before its local watcher sent the stop; that measure includes operating-system work and does not establish how many chess positions it searched. Confirmed native exit was **16.454–17.232 ms after D**. In eight controls the independent observer outside the frozen group stopped the native process while the group remained frozen and confirmed exit **9.576–10.981 ms before D**.

For the accepted hard cutoff, an ordinary delayed wake with the same original schedule must undergo the same truthful check as a late-discovered tighter schedule. If the first live check after a whole-system pause finds the old native process still present after D, stop it immediately, fence new dispatch, discard that interrupted game and report the actual late exit. If the timestamps are absent, report an unverified stop. Only a still-running independent observer can attest an earlier exit. A wake that stops the engine successfully now is not evidence that it was already gone at D. Keep separate records for a worker-only crash and an outage of the whole host; the fixture does not demonstrate how the rented host resumes.
