Findings (no engine bug found; nothing changed in the engine):
1. **Threads 2 can settle on a longer mate, and a warm TT keeps it** (not a correctness bug). For the mate in 3 above, 2 of 100 runs (earlier 1 of 60) of a two-thread depth-14 search reported mate in 4 or mate in 11. A second SMP search, and a single-thread d12 search on the same TT, kept that score. A fresh d12 search finds mate 3, and d20 on the warm TT finds it too. Every reported mate was real. Reproduction: tools/smp_mate_probe.cpp, logs/smp_mate_probe.log. The test therefore asserts only "real mate, never shorter than the truth" under SMP.
2. **Shortest mates are found late in simple endings** (search depth, not the TT). `8/8/4K2k/8/4R3/8/8/8 w` (unique mate in 3, Kf6) shows mate 4 at d8–12 and mate 3 from d13. `8/1k6/8/2K5/8/8/8/5Q2 w` (python-chess: mate in 3 with Qf7) shows mate 5 then 4 through d12. The mate-in-2 continuations are found at d3.
3. **Equal tablebase ranks:** searching a TB position again on the same TT may play another move of the same best rank (3 of 24 positions); the score is identical. The first test version demanded the same move (logs/tt_mate_tb_tables_strict_repeat_check.log); it now demands a move that keeps the result.
4. **UCI option names are case-sensitive.** `setoption name hash value abc` is ignored silently, while `Hash` reports invalid. The UCI description says names are not case-sensitive; GUIs send the advertised spelling, so this is a protocol nit. Not changed, and not asserted either way.
5. CorrExt changes no bench node count at depths 5–8, so its clamp is checked only as "silent".
