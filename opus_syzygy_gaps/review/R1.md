# R1 - independent review of syzygy_gaps_after_p6.patch (cand 188f8ff on ded9684)

Reviewer: opus-max, read-only. Nothing in any repository, source tree, fixture or tool was changed.

**Verdict on requirements 1-5: no violation found, so no BLOCKER.** Requirement 2 "with tables" is proven only cold and by reading (finding 9).
The serious findings are one real result loss the ledger calls sound, and test tools that cannot see it.

All engine and solver runs below were done here on existing exes (`out/exe/cand_v1_plain.exe` = macros on, `out/exe/p6_plain.exe` = parent, `out/exe/tb_claims_g2c.exe`) through `pinned.ps1`.
"Exhaustive truth" means the DTZ-free search in the appendix: it counts the clock by hand and uses WDL only after a zeroing move, so it does not depend on DTZ or on the `rounded` flag.

## Findings, most severe first

### 1. HIGH - a loser's rounded d + c = 100 draw is thrown away and shown as a TB loss, with every switch on
**Where:** `src/syzygy.inc:1157-1160` (`dtz_rank`, loss branch), `src/tablebase.inc:101-113` (no loss case), `GAP_LEDGER.md:19`, `README.md:43-45`.

**What is wrong:** rank -2000 covers every losing move with d + c <= 100. A rounded d + c = 100 can truly be 101, which is a 50-move draw, but it ranks with moves that really lose. So the kept set mixes drawing and losing moves, and the report says TB loss. The ledger line "selection is sound (0 of 19905 kept moves give up the result)" is false, and "OPEN (rounded loser)" is now RED. The behaviour comes from the parent, and this patch leaves it in place.

**Failing scenario:** `1B6/8/R7/4k3/8/8/K4Q2/8 b - - 96 49`, full tables.
- Kept: e5e4 and e5d5, both rank -2000.
- Exhaustive truth: e5e4 draws (child dtz 3, rounded), e5d5 loses (child dtz 1).
- `p6_plain` and `cand_v1_plain` (SyzygyRootExact 1, SyzygyTbBounds 7), depth 10: `score cp -31870`, `bestmove e5d5`.

Same result with:
- `8/8/2RNR3/5k2/8/8/7K/8 b - - 96 49` (plays f5e6; f5f4 and f5g4 draw)
- `8/K7/5B2/8/2k5/3Q3N/8/8 b - - 96 49` (plays c4d3; c4c5 and c4b4 draw)
- `1r6/5K2/1k2Q3/8/8/4R3/8/8 b - - 96 49` (plays b6a5; only b6a7 draws)

`2K5/8/8/R7/3B4/8/3k4/5Q2 b - - 98 50` has one legal move, Kc2, and is a true draw, but it is reported as -31870.

**Size,** on `clock.fens` rows with |root dtz| + clock = 100, highest clocks first until the time budget ran out:
- Report, 1026 rows solved: rounded losers 58 false TB loss, 169 true loss, 4 correctly -2. Exact losers 250 of 250 true.
- Moves: 39 of 440 loser roots keep a move that gives up the draw. The candidate at depth 10 played the losing move in 8 of those 39.

**How to verify:** run the FENs over UCI and compare with the appendix solver. These FENs are the missing RED fixture. A fix (rank rounded sum-100 loser moves above -2000, show -2) changes the move set, so it is a search change, not "report only".

### 2. HIGH - `root_check.py` and `root_move_check.py` switch off all checks for a root with one undecided move
**Where:** `tools/root_check.py:97-99, 123, 130, 139`, `tools/root_move_check.py:87-94`.

**What is wrong:** one undecided move, even a bad one, disables A, B and D for the whole root. 2418 of 19905 clock roots (12%) are never judged, and they are the boundary rows. This is why finding 1 reads as "0 A_bad".

In addition, "exact" against "undecided" comes from the engine's own `rounded` flag (`root_check.py:86-89`). python-chess and Fathom cannot see rounding, so a wrong flag cannot fail, and "python-chess and Fathom agree on the win" (ledger G5) does not check the exact class.

**Failing scenario:** re-judging the skipped rows with per-move low and high classes: 1126 of the 2418 have a best class that does not depend on the undecided move, and 10 of them have a wrong display (see finding 3). The other 1292 are table-undecided but solvable, and 812 of them display a TB loss. On promo: 41 skipped, 4 of them display a TB loss.

**How to verify:** judge each root on `[lo, hi]` per move. Replace the undecided class with the appendix solver, which is the independent check of the exact claims.

### 3. MEDIUM - rank 900 lumps true wins and draws, and `SyzygyRootExact` cannot show a win next to a rounded tie
**Where:** `src/syzygy.inc:1153-1154`, `src/tablebase.inc:107-108`, `README.md:24, 41-43`.

**What is wrong:** all sum-100 moves get rank 900 whether exact or rounded. A kept set can hold moves that draw next to a move that wins. With one rounded tie the report stays +2 even if an exact winning move exists, which contradicts "a win with exact dtz + counter = 100 is shown as a win". There is no false claim here. The result is at risk.

**Failing scenario:**

- `8/7K/7Q/5k2/6q1/2Q5/8/8 w - - 97 49`: display 2, decided win.

Size: 31 of 535 wdl = 2 roots at clock >= 95 keep such a mix. The candidate kept the win in all 26 tested at depth 10, on short distances where the search sees the draw at 100. Long distances were not tested.

**How to verify:** the appendix solver per kept move. Add a game from such a root at low depth.

### 7. MEDIUM - the G7 fixture is one-sided and root-only, and the decided subset is biased
**Where:** `tools/warm_claims.py:132-133, 40-43`, `out/exp/warm/subset.py`.

**New since the brief:** `p6_clock_d14` finished with false_warm 5, so G7 now has root-level RED. `cand_b7_r0`: 3. `cand_b7_r1`: no result yet.

**What is wrong:**

**Also (toggle mode, `warm_claims.py:78-88`):** the cold control uses `ucinewgame` (TT + histories), while bit 2 uses `clear_hash` (TT and evaluator caches only, `search.cpp:1556-1559`). A leftover class difference with bit 2 on can be a false alarm. No candidate toggle run exists yet.

## Appendix: the solver used as truth
Run with python-chess 1.11.2 and `D:\syzygy345`. It is DTZ-free. For long distances I also bounded it with dtz (sum <= 99 decided, sum > 100 draw, recurse only at sum 100). I checked that version against the DTZ-free search on six roots (c = 96 and 98).
```python
def val(b, c):                       # 1 win, 0 draw, -1 loss, side to move, clock c
    best, any_m = -1, False
    for m in list(b.legal_moves):
        any_m = True
        z = b.is_zeroing(m); b.push(m)
        if b.is_checkmate(): v = 1
        elif b.is_stalemate(): v = 0
        elif z:
            w = tb.probe_wdl(b); v = 1 if w == -2 else -1 if w == 2 else 0
        elif c + 1 >= 100: v = 0
        else: v = -val(b, c + 1)
        b.pop()
        best = max(best, v)
        if best == 1: break
    return best if any_m else (-1 if b.is_check() else 0)
```
