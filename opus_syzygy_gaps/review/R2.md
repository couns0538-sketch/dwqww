### 2. MEDIUM - the G7 residue reaches the root and changes the move, with every switch on
**Where:** `src/search.cpp:162-168`, `README.md:26`.

**Your explanation is right, with one refinement.** The cause is the score order, not only where the line ends. A loser prefers any TB loss to any mate loss, whatever the distance, so a move scored as a mate loss does not count towards k. k then does not bound DTZ. Evidence:
- `8/8/6K1/8/qB6/8/1Q6/6k1 w - - 79 40` and `Q7/8/8/8/8/3N4/3K3k/7q w - - 89 45`: the table-optimal line ends in mate at plies 23 and 13.
- `8/q7/8/8/8/3Q1RK1/k7/8 b` at clock 0, depth 12: root -31861 (k = 10), while a7g1 has child dtz 13 and that line ends `Qd1#` at ply 14.
- Two wrong positions have a table line ending in a capture: `8/8/2K5/4Q2R/k7/8/2q5/8 w - - 88 45` (ply 13) and `6K1/4q3/8/8/8/3N4/8/4N2k b - - 86 44` (ply 17, the null return of finding 1). This fits a winner preferring a longer mate there, but I did not prove it for these two.

**Failing scenario,** 3-4 piece tables, 3/3/3: `ucinewgame`, search `8/q7/8/8/8/3Q1RK1/k7/8 b - - 0 1`, then on the same table `8/q7/8/8/8/3Q1RK1/k7/8 b - - 87 44`.

| depth | warm | cold |
|---|---|---|
| 10 | `cp -31859`, a7c7 | `cp -397`, a7g1 |
| 12, 14, 16 | `cp -31861`, a7c7 | `cp 0`, a7g1 |

The solver gives a7c7 as a loss and a7g1 as the only drawing move, so the engine gives up the draw. The clock gap does not have to be large: a first search at clock 40, 70 or 80 does the same, at 85 or 86 it does not. Second row: `8/8/8/3k4/2R5/3K4/2N4N/8 b - - 87 44`, depth 14 and 16: warm TB loss with d5e5 (loss), cold d5d6 (draw). These are the 2 `false_warm` rows of `out/qual/v5on/warm_clock.log`. That run does not lose true claims: control 304 warm against 308 parent, target false 2 against 5.

**Is there a simple rule?**
- A DTZ check when reading does not close it. These nodes are above the loaded tables, and so would be the real case.
- A store-side rule should close it by induction, because k then bounds the longest line. It is about five lines behind `SyzygyRule50` bit 1, and it only raises a TB loss inside the band. **Not built and not tested** (no builds in this review):
```cpp
if (score <= -MateInMaxPly) mate_loss = std::max(mate_loss, score);          // move loop, mate_loss starts at -Infinite
if (mate_loss > -Infinite && best_score <= -syzygy::TbWinInMaxPly && best_score > -MateInMaxPly)
    best_score = std::max(best_score, -syzygy::TbWin + (MateValue + mate_loss));  // node end, before bound and store; qsearch evasions too
```
- `clock + 2 * entry.depth <= 100` on read is a one-liner, but only a heuristic.

**How to verify:** try the store-side rule against `h5` warm (35 wrong TT cuts must go) and `warm_clock` (target 2 to 0, control at least 304). If you keep it as a documented limit, `README.md:26` must change. Today it says such a score "is not used". It should say that k can understate the distance when a mate-scored line is longer, and that this can reach the root and change the move, naming the first FEN above.

## Answers to your questions, no finding
- **`top` early stop:** safe. The table winner's strategy guarantees at least a draw at any later clock, so a table loser can never reach +1. The recursion only runs at |dtz| <= 100, so only on WDL +-2, and `top` depends only on the position, so memo values are consistent.
- **Memo:** the key contains the clock. A slot collision only loses an entry, and a read needs the full code. `| 1` gives up one key bit, which is negligible. A budget stop returns before the store, so no partial value is kept.
- **Mate and stalemate:** tested before the clock, correct at clock 100 too.
- **`rounded`:** same meaning at the root and in the walk, both for the child. The sum uses the child's clock.
