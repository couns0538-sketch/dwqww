### 1. Store-side rule (`src/search.cpp:1236`, `:1281-1292`): sound, no false claim found
- **Band and sign.** The raise is `max(best_score, -TbWin + (MateValue + longest_mate_loss))`. Both distances count from the root. The guard keeps `best_score` in the TB loss band, and a mate ply of at most 128 keeps the raised value there too. The sign cannot change, so no win or draw can appear.
- **Direction.** Only the distance moves, and it moves longer. `tb_score_fits_clock` (`:162-169`) then refuses more, so the rule costs true claims and cannot add one.
- **`bound` is computed first (`:1281`).**
  - A BoundUpper raised over alpha returns >= beta on a null window.
  - A BoundExact raised may exceed beta, and the PV may then be truncated.
  - A BoundLower raised is an unproven lower bound in distance only.
  - All of these are negative TB-band values, so TB distance ordering is the only effect. Aspiration ends because delta grows.
- **TT store.** `score_to_tt` stores the raised value as a distance from the node, the same convention as before.
- **Rule off.** `options::syzygy_50_move_rule` gates it. I compared `out/exp/hunt/ruleoff_v8_0.jsonl` and `ruleoff_v8_1.jsonl` directly: byte-equal, 6000 rows.

### 6. LOW - `README.md:28` "covers every line of the node" overstates; two holes by reading, no failing scenario
**What is true:** the rule covers searched moves at non-root main-search nodes. `REVIEW_LOG.md:33` already says main search only.
- **Root (`search.cpp:1285` `!root_node`).**
  - A root inside the tables is normally never stored: `prepare_root` sets `search_moves_specified` and `:1290` skips the store (only the early returns at `tablebase.inc:79` and `:93` leave it unrestricted). A root above the tables is stored, unraised. This is the fixture setup, a 5-man root on `out/tb/man34`; on a real set it is a root with more pieces than the tables.
  - That entry can be read at a higher clock within one game. `Board::is_repetition(root_history_index_)` (`board.cpp:903`) needs two occurrences before the current root, so one earlier occurrence is not a draw at `search.cpp:946`. At the probe (`:963-967`) two gates apply: `score_usable` (`include/forge/search.hpp:83`) passes a different clock only if both clocks are below 90, and `tb_score_fits_clock` (`:162-169`) needs `k + clock <= 100`. A non-PV node then cuts on the entry (`:974`).
  - So a false claim needs a later clock of at most 89, a stored k with `k + clock <= 100`, and a mate line of the loser longer than `100 - clock` plies, which means at least 12 plies. It should be rare, but the path exists.
  - **I have no failing scenario.** The path can be driven over UCI with a warm hash, and my one run did that, but it had no power:
    - On `man34`, `8/q7/8/8/8/3Q1RK1/k7/8 b - - 0 1` as root at depth 12, then each of its 9 predecessors at clock 86 at depth 12: no false final score. But this root's k is 20 (cp -31851), so 87 + 20 > 100 and the read side refuses the entry, and all 9 predecessors have a true win anyway.
    - A scenario needs a P with a small k and such a mate line. I did not find one and stopped looking at the time limit.
    - Even with such a P, a final score shows only part of it, because a false cut in a PV line is searched again without the TT cut.
    - The claim harness cannot judge this path at its sites: it clears the table per row (`tools/tb_claims.cpp:83`), and its warm mode re-searches the same FEN, where the root is a PV node. So the 0 wrong in item 1 says nothing about this path. Judging it at the sites needs a warm mode with two FENs, which is a build and outside these rules.
- **qsearch.** There is no raise there. A TB loss reaches qsearch only through TT entries at in-check depth-0 nodes. 0 wrong in about 5.4M `tt_cut_qs` events; I did not construct a case.

**Suggested text:** "every searched move at a non-root main-search node". Whether to also raise the stored value at a root, without changing the returned score, is for you and Code Review. I would not change the code for this without a failing test.
